# 子 Agent 协作体系设计

> 状态：设计草案，未实现。日期：2026-11-11。
> 范围：标准化 workflow；主 agent 的动态调度；任务难度评估与子 agent 创建策略；子 agent 之间的通信与协调。
> 不含：具体代码实现、接口签名、存储格式。
> 标注约定：**【已核实】** 表示对照本仓库代码或文档核实过；**【背景知识】** 表示来自对主流方案的了解，没有逐一核对官方文档，落地前需要复核；文中所有数值都是**初始建议值**，需要用评测校准（见 6.5）。

## 0. 摘要

现在的子 agent 能力只有一种静态的 agent-as-tool（`AgentTool`）：子 agent 在代码里预先构造并固定，模型只能在已注册的子 agent 里选一个调用。没有 workflow，没有按任务难度动态创建子 agent 的能力，子 agent 之间也没有通信。

本设计分四块补齐：

1. **标准化 workflow**：统一的任务生命周期、任务单与交付物格式、六种编排模式、三道质量关口、失败处理阶梯（第 2 节）。
2. **动态调度**：主 agent 在运行中循环地评估、决策、派发、监控、重新评估，并受权限、预算、并发、深度的约束（第 3 节）。
3. **难度评估与创建策略**：六维难度画像换算成 L0–L4 等级，再由等级和可分解性决定"要不要创建、创建几个、各自负责什么"（第 4 节）。
4. **通信与协调**：星型拓扑、任务板与工件区、标准消息、冲突仲裁、三步汇总（第 5 节）。

**六条设计原则**，后面所有规则都从它们推出：

1. **默认单 agent，委派是有成本的例外**。多 agent 的 token 消耗通常是单 agent 的数倍，委派必须能证明收益。
2. **委派收益只来自四件事**：上下文隔离、并行加速、专业化（不同工具、权限、模型）、独立验证。
3. **权限只收窄不放宽**：子 agent 的权限和预算都不超过父 agent。
4. **一切可预算、可终止、可审计**：每次委派都有额度和终止条件，每个决策都留日志。
5. **传引用不传全文**：agent 之间交换的是任务单、摘要和工件引用。
6. **子 agent 的输出是数据，不是指令**：主 agent 不盲信，必须能核验。

## 1. 现状与差距

### 1.1 本项目现状【已核实】

依据 `src/agent/sub_agent.rs`、`docs/agent-gap-analysis.md`（第 4 项的执行记录）：

| 方面 | 现状 |
|---|---|
| 子 agent 的来源 | 构造时固定。`AgentTool::new(名称, 描述, agent)` 把已有的 `Agent` 包成工具，模型只能选用，不能创建 |
| 输入输出 | 输入只有一个 `task` 字符串；输出只有最终回答的文本 |
| 上下文 | 每次调用都是全新运行，看不到父对话，两次调用之间也互不记忆 |
| 并发 | 只有子 agent 的工具全部是 `concurrency_safe` 时才与同一轮的其他调用并发；并发数无整体上限 |
| 权限与审批 | 父 agent 的沙箱和审批**不继承**；子 agent 自己的钩子只管它自己的工具调用 |
| 预算 | 父 agent 把整次委派算作一轮；子 agent 按自己的 `with_max_steps` 运行，并发委派会成倍放大开销 |
| 取消与超时 | 父 agent 取消或工具超时，子 agent 的运行被丢弃 |
| 用量 | 已按子 agent 的模型计入父运行，失败的委派也计 |
| 观测 | 子 agent 的 `invoke_agent` span 挂在父的 `execute_tool` 下；但中间过程（token、工具调用）不出现在父的流式事件里 |
| 成环 | 构造不出循环，嵌套深度由调用方自己决定 |
| 编排 | 没有 handoff，没有 workflow / graph 编排；`update_plan`、`reflect` 只服务单个 agent 自身 |

### 1.2 与主流方案的差距【背景知识】

| 能力 | 主流做法 | 本项目 |
|---|---|---|
| 上下文隔离 | 子 agent 独立上下文，只回传摘要 | 已有 |
| 角色定义 | 每个子 agent 有自己的 prompt、工具白名单、模型、权限，主 agent 按描述自动选用 | 只能在代码里写死 |
| 运行时动态派生 | 主 agent 运行中按需拉起子 agent | 没有 |
| 并行 fan-out / fan-in | 同一轮并发多个子 agent，结果汇总 | 部分（只读子 agent，无上限） |
| 规模自适应 | 通常靠 prompt 里的规则让主 agent 判断，也有按难度把任务路由到不同档位模型的做法 | 没有 |
| Handoff | 把对话控制权转交给另一个 agent | 没有 |
| 编排模式 | prompt chaining、routing、parallelization、orchestrator-workers、evaluator-optimizer；图、顺序/并行/循环 agent | 没有 |
| 共享状态与通信 | 共享 state、session state、工件传引用；agent 间协议；teammate 互发消息 | 没有 |
| 持久化与恢复 | 子 agent 可 resume、可后台、可中断等人 | 主 agent 有，子 agent 没有 |
| 权限收窄与隔离 | 最小权限、独立工作区或容器、hooks | 不继承，只在构造时打 warn |
| 防失控 | 并发、深度、预算限制；子 agent 不能再派生 | 有超时和 `max_steps`，无全局上限 |
| 结构化交付与验证 | 结构化结果，独立 reviewer / verifier | 只有文本 |
| 观测与成本 | 嵌套 trace，按 agent 统计成本 | 已有 |

**结论**：隔离、计费、trace、超时、取消、审批这些基础是完整的；缺的是**动态派生、编排、共享状态**三层，以及把基础能力**继承**给子 agent 的治理层。

## 2. 标准化 Workflow 机制

### 2.1 统一生命周期

所有委派任务走同一条流水线，区别只是某些阶段是否简化。

| 阶段 | 责任方 | 输入 | 输出 | 出口准则 |
|---|---|---|---|---|
| ① 接收 | 主 | 用户请求 | 明确的目标与约束 | 目标可判定；歧义已澄清或做了显式假设 |
| ② 评估 | 主 | 目标 | 难度画像和等级（第 4 节） | 已产出等级、形态、预算 |
| ③ 拆解 | 主 | 等级与形态 | 子任务清单（含依赖、角色、验收标准） | 子任务职责互斥、合起来覆盖目标 |
| ④ 派发 | 主 | 子任务 | 任务单 | 每张任务单字段完整，预算已预留 |
| ⑤ 执行 | 子 | 任务单 | 过程事件、工件 | 达到验收标准，或触发终止条件 |
| ⑥ 交付 | 子 | 执行结果 | 标准交付物 | 交付物字段完整 |
| ⑦ 核验 | 主或 Verifier | 交付物 | 通过、退回或升级 | 满足验收标准且证据可查 |
| ⑧ 汇总 | 主 | 已核验的交付物 | 面向原始问题的最终答案 | 无未标注的冲突和缺口 |
| ⑨ 复盘 | 主 | 全程记录 | 决策日志、成本、偏差 | 已写入日志，供评估和调参使用 |

**任务状态机**：`草拟 → 就绪 → 执行中 →（阻塞）→ 已交付 → 已验证`；异常出口为 `失败`、`已取消`、`已升级`（交人处理）。

### 2.2 任务单（Task Brief）

子 agent 看不到父对话，任务单必须自成一体。

| 字段 | 内容 |
|---|---|
| 目标 | 一句话主问题；一个任务单只有一个主问题 |
| 背景摘要 | 完成任务所需的最少上下文，其余用引用 |
| 输入引用 | 文件路径、工件 ID、上游交付物 ID |
| 范围边界 | 做什么、不做什么，可触碰的资源范围 |
| 约束 | 风格、格式、禁止项 |
| 完成标准 | 可检查的验收条目 |
| 交付格式 | 与 2.3 一致 |
| 资源额度 | 轮次、token、时间、成本上限 |
| 权限 | 工具白名单；是否可写；写入范围 |
| 依赖与优先级 | 前置任务、截止时间 |

### 2.3 交付物（Deliverable）

| 字段 | 说明 |
|---|---|
| 状态 | `完成` / `部分完成` / `阻塞` / `失败`，并说明原因 |
| 结论摘要 | 直接回答任务目标，不复述过程 |
| 证据 | 来源、文件位置、命令输出的引用 |
| 产出物 | 工件引用，不内嵌大段内容 |
| 置信度与未决项 | 确定的、不确定的、没覆盖到的 |
| 资源消耗 | 轮次、token、耗时 |
| 建议后续 | 可选，是否采纳由主 agent 决定 |

**硬规则**：没有证据的结论一律标为"未证实"。

### 2.4 标准编排模式

模板是可声明的预设：名称、触发条件、阶段、角色、关口、终止条件、默认预算。内置六种：

| 模式 | 结构 | 适用 | 终止条件 |
|---|---|---|---|
| A 直接执行 | 主 agent 自己做，无委派 | L0 / L1 | 完成 |
| B 探索汇总 | 多个只读 Explorer 并行，主 agent 汇总 | 信息收集、代码调研、多源检索 | 全部返回，或达到法定数 |
| C 流水线 | 阶段 1 → 关口 → 阶段 2 → …… | 强依赖的多步任务 | 最后阶段通过核验 |
| D 编排者-工人 | 主 agent 动态拆解，工人并行，Verifier 复核 | 复杂且可分解 | 全部验收通过 |
| E 实现评审循环 | Implementer 与 Reviewer 往复，最多 N 轮 | 质量敏感的产出 | 评审通过，或达到轮数上限后升级 |
| F 多方案竞争 | 同一目标多个视角并行，择优或融合 | 仅 L3 / L4 且方案不确定时 | 评审选出最优方案 |

### 2.5 三道质量关口

不通过不进入下一阶段。

1. **计划关口**（拆解后）：子任务是否互斥、是否覆盖目标、总预算是否在范围内。
2. **交付关口**（交付后）：字段完整、证据齐全、满足验收标准。
3. **汇总关口**（汇总前）：有无未解决的冲突，有无超出任务单范围的行为。

### 2.6 失败处理阶梯

| 失败类型 | 处理 |
|---|---|
| 输出不合规（缺字段、无证据） | 退回重做一次，附明确缺口 |
| 执行失败、超时 | 同角色重试一次；仍失败则换更强模型档位或换角色 |
| 任务单有歧义导致的偏差 | 改任务单后重派，不是原样重试 |
| 预算耗尽仍未完成 | 收取部分结果，标为"部分完成"，由主 agent 决定补派或降级 |
| 越权或违规行为 | 立即终止该子 agent，丢弃其产出，记录事件，通知用户 |
| 同一子任务连续失败 2 次 | 升级：主 agent 自己接手，或交人处理 |

**止损规则**：累计消耗超过预算的 80% 而整体进度不足 50% 时，触发重新规划。

## 3. 主 Agent 动态调度

### 3.1 调度循环

调度不是一次性决策，而是循环：

```
评估 → 决策形态 → 创建/派发 → 监控 → 重新评估 ─┐
  ▲                                             │
  └──────────────── 触发条件命中 ───────────────┘
```

### 3.2 决策输入与输出

| 类别 | 内容 |
|---|---|
| 任务特征（输入） | 难度画像（4.1 的六个维度） |
| 系统状态（输入） | 剩余预算、当前并发占用、已存在的子 agent、历史失败记录 |
| 决策（输出） | 委派形态（不委派、单个、并行 N 个、流水线、编排者-工人）；各子任务的角色、模型档位、权限、预算 |

### 3.3 重新评估触发点

| 触发 | 动作 |
|---|---|
| 子 agent 回报"任务比预期大" | 等级上调，重新拆解 |
| 发现新的独立子任务 | 追加派发，受总数上限约束 |
| 子 agent 报告阻塞 | 解阻（补信息）、换角色或升级 |
| 多个子 agent 结论冲突 | 触发取证（5.6） |
| 预算消耗与进度偏离 | 触发止损规则 |
| 任务比预期简单 | 终止多余的子 agent，降级为直接执行 |

### 3.4 调度权限边界

| 项目 | 规则 |
|---|---|
| 谁能创建 | 默认只有主 agent；子 agent 默认不可再派生 |
| 嵌套深度 | 默认 1 层；仅 L4 的"阶段编排者"允许再派生一层，深度上限 2 |
| 不可递归 | 任何 agent 不能派生同角色同任务单的副本 |
| 预算继承 | 子预算不超过父剩余预算；子 agent 再派生时只能从自己的预算里分 |
| 权限继承 | 子权限是父权限的子集，沙箱和审批规则同样继承 |
| 需用户确认 | 预计总开销超过单 agent 估算的 3 倍；或存在 R=3 的高风险写操作 |

## 4. 任务难度评估与创建策略

### 4.1 难度画像：六个维度（各 0–3 分）

| 维度 | 0 | 1 | 2 | 3 |
|---|---|---|---|---|
| **S 规模**（范围加上下文体量） | 单点，几千 token 内 | 少量文件或来源 | 多模块，约占窗口一半 | 大面积，必然超窗口 |
| **C 认知难度**（推理深度加不确定性） | 确定性操作 | 常规推理 | 需要权衡或调研 | 开放问题，多路径，高不确定 |
| **E 资源需求**（预计工具轮次） | 少于 5 轮 | 5–15 轮 | 15–40 轮 | 超过 40 轮 |
| **P 可分解性** | 不可分 | 弱可分，有强依赖 | 部分切片独立 | 多个独立切片 |
| **R 风险** | 只读 | 小范围可逆写入 | 大面积写入或执行命令 | 不可逆或有外部影响 |
| **V 验证难度** | 可自证（测试、计算） | 易检查 | 需要判断 | 难以验证 |

### 4.2 等级计算

```
基础等级 = max(S, C, E)                          → L0 ~ L3
修正     = R=3，或 (V=3 且 基础等级≥2)  →  等级 +1（上限 L4）
形态倾向 = P ≤ 1 → 串行形态；P ≥ 2 → 并行形态
```

| 等级 | 含义 | 典型任务 |
|---|---|---|
| L0 | 微任务 | 一问一答，单次计算 |
| L1 | 简单 | 单一来源，少量工具调用 |
| L2 | 中等 | 多文件调研、需要隔离上下文的子问题 |
| L3 | 复杂 | 跨模块改动、多源研究、需要独立验证 |
| L4 | 极复杂或高风险 | 大型重构、带不可逆操作的流程 |

### 4.3 快速判定树

评分之前先过一遍：

```
Q1  自己 ≤5 轮工具调用、上下文不会膨胀？          是 → 直接执行
Q2  过程会产生大量中间噪声，或将撑爆上下文？       是 → 至少委派一个 Explorer 做隔离
Q3  有 ≥2 个互相独立的子任务？                    是 → 并行 fan-out
Q4  子任务有强依赖？                              是 → 串行流水线
Q5  有副作用且难回滚？                            是 → 单写者 + 审批 + Verifier
Q6  结果难以自证？                                是 → 加独立 Verifier
```

### 4.4 何时创建，何时不创建

**创建的四类理由**，至少满足一条才有资格委派：

| 理由 | 判定 |
|---|---|
| 隔离 | 中间产物体量远大于结论体量 |
| 并行 | 存在 2 个以上独立切片，并行节省的时间大于协调开销 |
| 专业化 | 需要不同的工具、权限或模型档位 |
| 独立验证 | 需要不受原上下文影响的复核 |

**不创建的情形**：

- 任务小于委派的固定开销（启动、写任务单、读交付，约合 3–5 次工具调用）。
- 子任务强耦合，需要共享大量上下文。
- 需要和用户来回对话式迭代。
- 多个子任务要写同一资源。
- 剩余预算不足，或已达并发、数量、深度上限。

**委派收益测试**：预期节省（时间、主上下文占用、质量增益）必须大于委派开销乘以安全系数 1.5，否则不委派。

### 4.5 创建多少个

```
N = min( 独立子任务数, 档位上限, 全局并发余量, 预算可支撑数 )
```

| 等级与形态 | 工人数 | 附加角色 |
|---|---|---|
| L0 / L1 | 0 | 无 |
| L2，P ≤ 1 | 1 | 无 |
| L2，P ≥ 2 | 2–3（并行） | 无 |
| L3，P ≤ 1 | 流水线 2–3 阶段，每阶段 1 个 | +1 Verifier |
| L3，P ≥ 2 | 3–5（并行） | +1 Verifier |
| L4 | 分阶段，每阶段最多 5 个 | 每阶段 Verifier，阶段间人工检查点 |

**Verifier 与审批的附加规则**：V ≥ 2 或 R ≥ 2 时加独立 Verifier；R ≥ 2 的写入一律经审批。

**四条修正规则**：

1. **宁少勿多**：先小规模探测，信息不足再扩大。
2. **合并过小的**：子任务小于委派开销就合并。
3. **继续拆过大的**：子任务预计占用超过单个 agent 上下文 60% 就继续拆。
4. **单写者**：同一可写资源同一时刻只允许一个写者，其余角色只读。

**全局上限（初始值）**：同时活跃子 agent ≤ 5，单次任务累计创建 ≤ 12。

### 4.6 如何分配职责

**先选切分轴，再沿轴切**：

| 切分轴 | 适用 | 例 |
|---|---|---|
| 按信息源或模块 | 并行探索 | 每个 Explorer 负责一个目录或一类来源 |
| 按阶段 | 强依赖 | 调研 → 方案 → 实现 → 测试 |
| 按角色 | 质量保障 | 实现者与评审者分离 |
| 按视角 | 方案不确定 | 同一问题的不同解法并行 |

**职责规则**：

- 职责互斥，合起来覆盖目标。
- 一个任务单只有一个主问题。
- 边界显式写入任务单（做什么、不做什么）。
- 同类子 agent 使用统一的交付格式，便于汇总。
- **Verifier 必须与被验证者分属不同上下文**，模型档位不低于被验证者。

### 4.7 角色目录

| 角色 | 权限 | 模型档位 | 典型交付 |
|---|---|---|---|
| Explorer | 只读（文件、检索） | 轻量 | 发现清单加位置引用 |
| Researcher | 只读加联网检索 | 轻量到中等 | 带来源的结论 |
| Planner | 只读 | 强 | 方案和任务拆解建议 |
| Implementer | 受限写入（限定路径），需审批 | 中等到强 | 变更及自证 |
| Runner | 受限命令执行，需审批 | 轻量到中等 | 命令结果摘要 |
| Verifier | 只读，可运行测试 | 不低于被验证者 | 通过或不通过，加证据 |
| Integrator | 只读 | 中等 | 合并多份交付为一份 |

角色模板规定**最大权限**，创建时只能在模板内收窄，不能放宽。

### 4.8 模型档位策略

- 探索、检索、汇总类用轻量模型，控制成本。
- 规划、复杂实现、评审用强模型。
- 升级规则：同一子任务失败一次，下一次升一档。
- 降级规则：连续 3 次同类任务在低档位一次通过，该类任务默认降一档。

### 4.9 预算分配

```
总预算 B（token、成本、时间）
 ├─ 保留 20%：汇总、返工、重试
 └─ 可分配 80%：按子任务估算权重分配
       单个子 agent ≤ 可分配的 30%
```

- 子 agent 需要追加预算时，先向主 agent 申请，不能自行扩张。
- 预算耗尽即终止，已完成的部分作为"部分完成"交付。

### 4.10 示例

| 任务 | 画像 | 决策 |
|---|---|---|
| "这个函数是做什么的" | S0 C1 E0 | L1，直接执行 |
| "梳理 5 个模块的错误处理现状" | S2 C1 E2 P3 R0 V1 | L2，3 个并行 Explorer，无 Verifier |
| "把鉴权从方案 A 迁移到 B，涉及 8 个模块" | S3 C2 E3 P2 R2 V2 | L3：Planner 出方案，再由 3–4 个 Implementer 按模块并行（各自限定写入路径），最后 Verifier 复核；写入全部需审批 |

## 5. 通信与协调

### 5.1 基本拓扑

**默认星型**：主 agent 是唯一枢纽，子 agent 之间不直接通信。

- 信息流可审计，冲突有唯一仲裁者，权限边界清晰。
- 例外：L4 流水线的相邻阶段可以通过"交接工件"传递，但仍经任务板登记，不走私聊。

### 5.2 通信通道

| 通道 | 方向 | 性质 | 内容 |
|---|---|---|---|
| 任务单 | 主 → 子 | 一次性 | 2.2 的字段 |
| 交付回报 | 子 → 主 | 终态 | 2.3 的字段 |
| 进度事件 | 子 → 主 | 异步、轻量 | 开始、里程碑、阻塞、完成，附估计剩余量 |
| 澄清请求 | 子 → 主 | 阻塞式 | 具体问题加已尝试的假设；主 agent 可回答、拒绝或转交用户 |
| 调整指令 | 主 → 子 | 异步 | 取消、缩小范围、追加预算、补充信息 |
| 任务板 | 双向受限 | 共享状态 | 所有任务的状态、依赖、负责人、结果引用 |
| 工件区 | 双向受限 | 共享存储 | 大体量产出，版本化、只追加 |
| 发现广播 | 子 → 任务板 | 可选 | 对其他任务有价值的中间发现，附来源和置信度 |

**消息信封**（所有通信的统一头部）：发送者、接收者、任务 ID、消息类型、优先级、内容或引用、是否需要响应、版本号、时间戳。

### 5.3 信息同步规则

**读写矩阵**：

| 对象 | 主 agent | 子 agent |
|---|---|---|
| 任务单 | 读写 | 只读自己的 |
| 任务板 | 读写 | 读全局，写自己任务的状态 |
| 工件区 | 读写 | 写自己的命名空间（只追加），读依赖声明的上游工件 |
| 发现广播 | 读写、审核 | 写；读取需任务单授权 |
| 用户对话历史 | 读写 | 不可见，只拿到主 agent 提炼的背景摘要 |

**一致性规则**：

- 单一写者：同一资源同一时刻一个写者。
- 版本号：工件更新必须带版本，过期写入被拒绝。
- 仲裁权：冲突由主 agent 裁决。
- 共享"事实"必须带来源和置信度；过期的事实标注失效。

### 5.4 协调模式

| 模式 | 规则 |
|---|---|
| 依赖调度 | 按依赖的拓扑序派发，上游未验证不启动下游 |
| 屏障同步 | 三选一：全部到齐、法定数（如 3 取 2）、先到先得 |
| 超时降级 | 屏障等待有上限，超时按已到结果推进并标注缺口 |
| 任务认领 | 子任务只能被一个子 agent 认领，防重复劳动 |
| 竞争择优 | 方案竞争模式下，由 Verifier 按评分维度择优或融合 |
| 去重 | 相同发现合并，保留证据最强的一条 |

### 5.5 异常处理

| 异常 | 处理 |
|---|---|
| 子 agent 超时或失联 | 终止，取已有的部分结果，重派或降级 |
| 输出不合规 | 退回一次，仍不合规则丢弃 |
| 请求越权 | 拒绝并记录；多次越权则终止 |
| 请求需要审批的操作 | 冒泡到用户（5.8） |
| 澄清请求过多（超过 2 次） | 说明任务单有缺陷，主 agent 重写任务单 |

### 5.6 冲突处理

| 冲突 | 处理 |
|---|---|
| 子 agent 结论互相矛盾 | ① 检查证据；② 仍无法判定则派 Verifier 取证；③ 按"证据强度 > 来源可靠度 > 多数"裁决；④ 仍无法裁决则**保留分歧并向用户标注**，不静默选一边 |
| 资源冲突（同时要写） | 转为串行，或划分写入范围 |
| 范围越界 | 终止并丢弃越界产出 |
| 重复劳动 | 任务认领制避免；发生后合并结果 |

### 5.7 结果汇总

**三步**：

1. **收集校验**：检查格式、完成标准、证据；不合格的退回。
2. **归并**：去重、对齐口径、标注冲突。
3. **综合**：面向用户的**原始问题**重新组织答案，不是转述各子 agent 的话。

| 汇总策略 | 适用 |
|---|---|
| 拼接型 | 各子任务产出互不重叠（按模块分工） |
| 择优型 | 方案竞争 |
| 投票型 | 判断类任务的多视角复核 |
| 综合型 | 调研类，需要整合成统一结论 |

**最终输出必须包含**：结论、依据、未解决项、冲突与分歧、各子 agent 的贡献与消耗。

**不盲信原则**：主 agent 对关键结论抽检并要求引用证据；证据缺失的结论不进入最终答案，或明确标注"未证实"。

### 5.8 对用户透明与审批冒泡

- 子 agent 的进度事件对前端可见（任务板视图）。
- **子 agent 需要审批的操作，统一冒泡到主会话的审批通道**，由用户决定；没有人应答时主运行挂起并落盘。这是对现状的修正：现在子 agent 的审批不会冒泡，也不能让父 agent 挂起。
- 挂起状态必须包含各子任务的状态和已交付的工件，恢复后继续，不重做。

## 6. 治理（贯穿四块）

### 6.1 限额总表（初始值）

| 项目 | 默认 | 说明 |
|---|---|---|
| 全局并发子 agent | 5 | 超出排队 |
| 单次任务累计创建 | 12 | 超出需用户确认 |
| 嵌套深度 | 1（L4 阶段编排者最多 2） | 子 agent 默认不可再派生 |
| 单子 agent 预算 | 不超过可分配预算的 30% | 追加需申请 |
| 保留预算 | 20% | 汇总与返工 |
| 失败重试 | 每子任务最多 2 次 | 超出升级 |
| 评审循环 | 最多 3 轮 | 超出升级 |

### 6.2 熔断与防失控

- **无进展检测**：连续 N 轮无新增证据或工件，视为无进展，终止。
- **重复委派检测**：与已有任务单近似重复的派发请求被拒绝。
- **成本熔断**：累计成本超过预算的 100% 立即停止派发新任务。
- **全局急停**：用户取消时，取消信号传播到所有活跃子 agent，已执行的部分标注"可能已生效"。

### 6.3 安全

- 权限只收窄不放宽；沙箱和审批规则对子 agent 同样生效，子 agent 不再是绕过父 agent 的后门。
- 写操作单写者，高危操作必须冒泡审批。
- 子 agent 的输出视为不可信数据：不作为指令执行，不能直接写入长期记忆（沿用现有 `RememberGuard` 的思路）。
- 子 agent 的错误信息在回传前截断并脱敏。

### 6.4 可观测

- 嵌套 trace：主 → 子 → 工具，沿用现有 span 体系。
- 按 agent、按角色、按模型统计用量与成本，沿用现有用量账本。
- **决策日志**：每次委派记录难度画像、等级、选择的形态、理由、预算；每次**不委派**也记录原因，便于复盘误判。
- 任务板可视化。

### 6.5 评估指标

| 指标 | 衡量 |
|---|---|
| 委派收益 | 同一任务集上，多 agent 与单 agent 在成本、质量、时延上的对比 |
| 评估准确率 | 难度等级与事后实际消耗的偏差 |
| 拆解质量 | 返工率、子任务重叠率、遗漏率 |
| 子 agent 成功率 | 按角色、按模型档位分别统计 |
| 预算超支率 | 超出分配预算的任务占比 |
| 冲突率与仲裁结果 | 衡量验证机制是否有效 |

用一组固定任务做 A/B（单 agent 与多 agent），可并入第 14 项"真实 LLM 端到端回归评测"。**评估结果驱动调参**：第 4 节的阈值和 6.1 的上限都靠它校准。

## 7. 与现有机制的关系

| 现有机制 | 在本设计中的角色 |
|---|---|
| `AgentTool`（第 4 项） | 一期动态派生的基础；需要补上运行时创建、权限和预算继承 |
| `update_plan` / `reflect`（第 4 项） | 拆解结果可用 `update_plan` 呈现；`reflect` 可用于汇总关口前的自检 |
| 用量账本与嵌套 span（第 5 项） | 直接复用，按子 agent、角色、模型统计 |
| 审批与挂起恢复 | 扩展为审批冒泡，并把子任务状态纳入挂起状态 |
| `WorkspaceGuardCallback` | 作为权限继承的基础，子 agent 沿用同一工作区边界 |
| 取消与超时（第 2 项） | 全局急停和单子 agent 终止的基础 |
| 上下文预算（`ContextOptimizer`） | 任务单的背景摘要应控制在子 agent 上下文的合理比例内 |
| 第 14 项（端到端评测） | 承载 6.5 的 A/B 评估 |
| 第 9 项（Agent 作为 MCP Server） | 无直接依赖；二者都要决定"非交互场景下需要审批的工具怎么办"，审批冒泡的结论可以共用 |

## 8. 落地分期

每期都可以独立上线，后一期依赖前一期的基础。

| 期 | 内容 | 验收标准 |
|---|---|---|
| **一期：能委派** | 角色目录；任务单与交付物标准；运行时动态创建（单层、并行只读）；预算与权限继承；并发与数量上限；决策日志 | 复杂调研类任务上，多 agent 在质量或主上下文占用上优于单 agent；预算无越界；子 agent 不能超出角色模板的权限 |
| **二期：能协调** | 任务板、工件区、进度事件、澄清通道；审批冒泡；子任务状态随挂起落盘 | 写操作类任务全程可审计；挂起恢复后不重做已完成的子任务；前端能看到任务板 |
| **三期：能编排** | 六种 workflow 模板；难度评估规则化；模型档位路由；Verifier 与评审循环 | 评估准确率达标；Verifier 能拦截人为埋入的缺陷；各模式有端到端测试 |
| **四期：能自优化** | 方案竞争；L4 阶段编排与人工检查点；基于日志的阈值调参 | 在固定任务集上，成本与质量的曲线持续改进 |

## 9. 待决策项

| # | 问题 | 建议 |
|---|---|---|
| 1 | 难度评估由谁做 | 先由主 agent 按本文规则自评，加硬性上限护栏；有足够日志后再考虑独立的路由器 |
| 2 | 子 agent 是否可续接（有状态） | 一期不要，保持"一次性"；二期通过任务板和工件区实现"接力"，而不是长对话 |
| 3 | 审批冒泡的默认策略 | 写入、执行类全部冒泡；只读类不冒泡 |
| 4 | 初始并发和数量上限 | 采用 6.1 的值，上线后按指标调整 |
| 5 | 是否允许用户自定义角色和 workflow | 允许，但权限不得超出内置模板的最大权限 |
| 6 | 多方案竞争模式是否开放 | 先不开放，等 Verifier 稳定后再开 |
| 7 | 子 agent 的中间过程是否进入父 agent 的流式事件 | 进度事件进，细粒度 token 和工具调用不进；是否需要折叠展示留给前端设计 |

## 10. 不在本设计范围

- 具体的数据结构、接口签名、存储格式、事件协议。
- 跨进程或跨机器的 agent 通信协议（本设计默认同一进程内协作）。
- Handoff（把对话控制权转交给另一个 agent）：本设计以主 agent 持续持有对话为前提，不引入控制权转移；如有需要作为单独议题。
