## 0. 摘要

**使用定位**：`run_python` 是“能力缺口兜底工具”。Agent 处理任务时，现有工具都做不了，才现场写一段 Python，放进沙箱执行，拿到结果再继续。所以方案的重心是：代码是一次性的、没人事先审过；失败重试是常态；依赖和联网需求无法预知；结果要可靠、精简地回到模型。宿主工具桥接是次要需求（详见 1.4）。

1. **隔离形态**：进程级 OS 沙箱。macOS 用 Seatbelt；Linux 用 bubblewrap（命名空间）叠加 Landlock 与 seccomp；Windows 用 AppContainer 加 Job Object。不依赖 Docker 或虚拟机。后端抽象成 `SandboxBackend`，以后可以接容器或 microVM（轻量虚拟机）。
2. **通信**：宿主与沙箱之间只有一条**继承下来的双工流**（Unix 上是 `socketpair`，Windows 上是命名管道句柄），上面跑**带长度前缀的 JSON-RPC 2.0**。双方都能发起请求。通道里不放 TCP 端口、不放文件路径，也不使用 pickle。
3. **宿主能力（次要路径）**：工具和 skill 以“代码即 API”的方式暴露给 Python（参考 Anthropic 的 code execution with MCP）。默认关闭，按调用在 `needs.bridge` 里声明才可用；每次桥接调用都经过**与 Agent 直接调用相同的策略链**（路径守卫、MCP 守卫、审批），绝不绕过。
4. **默认受限，按需申请**：沙箱基线是“空房间”：只能写本对话的工作目录、临时目录和 `outbox`，宿主文件系统不可见，**网络关闭（已定：默认不能联网）**，只有预置依赖。需要更多（联网、读用户文件、把结果写回工作区）时，Agent 在调用里用 `needs` 声明，由人批准，只对这一次调用生效。没有声明升级项的基线调用**自动执行**（已定，1.4.3）。依赖方面，首版靠**做厚的预置依赖档**覆盖常见任务，按需装包（`needs.packages`）后置，等审计数据证明缺包是高频失败原因再做（9.6）。
5. **文件传递**：小数据走 RPC 内联；大数据和二进制走 `inbox`/`outbox` 目录交换；用户文件按 `needs.read` 复制进沙箱，结果按 `needs.exports` 由宿主复制回工作区。长期共享目录（ro/rw/stage）是运维配置的可选项。回收产物时宿主逐项校验（拒绝符号链接、限制数量与大小）。
6. **失败即关闭（fail-closed）**：后端不可用（内核太旧、用户命名空间被禁、AppContainer 授权失败）时拒绝运行，除非用户显式降级。静默降级是最危险的退化方式。
7. **与此前计划的差异**：此前倾向把 `birdcage` 作为首选封装。本次核实发现它**已于 2026-07-06 归档、许可证 GPL-3.0、不支持 Windows**，因此**不再推荐**。本方案改为自有的薄后端层，参考 Anthropic `sandbox-runtime` 与 OpenAI Codex 的做法。详见 2.1 和 2.3。
8. **社区实践对照**：“让模型写代码来完成任务”在社区有两条线：代码作为**主要动作空间**（smolagents、OpenHands CodeAct、Cloudflare Code Mode、Pydantic Monty），和代码作为**临时补位工具**（Anthropic 的 code execution tool、Claude Code 的沙箱 bash）。本方案属于后者。已读过一手资料的做法里，“默认无网络、预置依赖、每次空输出目录、先划边界再减少审批”都与本方案一致；差异和启示（预置依赖要做厚、审批与运行中代码的另一种配合方式、凭据不进沙箱）见 2.4。

## 1. 背景、目标与威胁模型

### 1.1 现状（代码事实）

| 事实 | 位置 | 对本方案的含义 |
|---|---|---|
| `run_command` 用 `sh -c`（Windows 为 `cmd /C`）执行任意命令，没有进程隔离，只靠审批拦截 | `src/tools/shell/execute.rs` | 这是当前最大的安全缺口；Python 沙箱应共用同一个后端层 |
| 现有的“沙箱”只是调用前的路径守卫：`WorkspaceGuardCallback`、`McpGuardCallback` | `src/callback/path_guard.rs`、`mcp_guard.rs` | 两者是不同层次，不能互相替代。CLI 的 `--no-sandbox` 只关这一层，命名需要避开 |
| `Tool::execute(&self, args_json)` 只拿到原始参数，没有 `ExecutionContext` | `src/tools/tool.rs` | 沙箱里发出的嵌套调用要走策略链，需要另想办法拿到上下文（见 6.3） |
| 策略链在 `Agent::execute_tool_calls` 中执行；`Suspend` 表示“现在无法决定，稍后恢复” | `src/agent/runtime/mod.rs`、`src/agent/callback.rs` | 活着的 Python 进程**不能被挂起再恢复**，嵌套调用必须把 `Suspend` 当作拒绝 |
| 用量记账靠 task-local，`tokio::spawn` 出去的任务记不上账 | `src/agent/usage.rs` | 桥接处理必须跑在发起 `run_python` 的同一个任务里 |
| 取消方式是丢弃 future；`run_command` 用守卫对象杀整个进程组 | `execute.rs` 的 `ProcessGroup` | 沙箱沿用“守卫 + Drop 回收”的模式 |
| 输出受限：首尾保留，中间截断（stdout 32 KiB、stderr 16 KiB） | `execute.rs` 的 `Capped` | 直接复用 |
| stdio MCP 子进程用 `env_clear` 加白名单环境变量 | `src/tools/mcp/config.rs` 的 `INHERITED_ENV_VARS` | 沙箱环境变量沿用同一思路（比 `strip_secrets` 的黑名单更严） |
| 仓库里**还没有 skill 概念**（全库检索无命中） | - | 本方案需要定义最小的 skill 注册与挂载（6.5） |
| `libc` 只在 `cfg(unix)` 下依赖；Windows 没有进程隔离的代码 | `Cargo.toml` | Windows 后端要新增依赖 |

### 1.2 目标与非目标

目标：

- G1：Agent 生成的 Python 在 OS 强制边界内运行，越权访问由内核拒绝，而不是靠约定。
- G2：Agent 与沙箱内进程能双向通信，包括执行期间的事件、嵌套调用和跨调用的会话。
- G3：沙箱内代码能调用宿主的工具和 skill，且不绕过现有审批与路径守卫。
- G4：默认对宿主受限；共享目录、网络、桥接工具均可配置。
- G5：Windows、macOS、Linux 都有可用的后端，能力差异显式声明，不隐藏。
- G6：作为缺口兜底工具，“写代码、运行、拿结果、出错重试”这个循环要又快又顺：启动开销有明确预算（`base` 档目标是毫秒级到数十毫秒，`data` 档按导入耗时分档；具体数值未实测，作为 P0a 的验收项，见 15.1），错误能让模型直接据此改代码，缺依赖、要联网、要处理用户文件时能自助申请，而不是死路一条。

非目标：

- N1：不防御内核或硬件级漏洞，不防御侧信道。多租户或不可信的第三方部署请使用容器或 microVM 后端（见 2.2）。
- N2：不防御拥有本机管理员权限的攻击者。
- N3：不替代人工审批。沙箱缩小爆炸半径，审批决定要不要做。
- N4：不做语言层沙箱（RestrictedPython、audit hook）。它们只是辅助，不算边界。
- N5：本文不规定具体代码和安装步骤。

### 1.3 威胁模型

| 项 | 内容 |
|---|---|
| 要保护的资产 | 宿主文件（`~/.ssh`、`.env*`、`.git/`、`.agent/`、`mcp.json`）；宿主环境变量里的 API key；宿主网络位置（内网、云元数据地址）；宿主的计算资源；经桥接可达的写入与执行类工具 |
| 攻击者 | 不可信的 Python 代码：模型手误、提示注入引导生成的恶意代码、被投毒的第三方 skill 脚本、被投毒的依赖 |
| 攻击者能力 | 在沙箱内任意执行代码；读写沙箱内已授权的路径；构造任意 RPC 帧；起任意多的子进程和线程 |
| 信任边界 | 宿主进程可信；沙箱内的一切（含 SDK）不可信；通道两端都不信任对方的输入，宿主必须校验每一帧 |
| 主要风险面 | 文件系统逃逸、网络外泄、桥接提权（confused deputy，被借权的代理人）、资源耗尽、通道协议攻击、经输出的间接提示注入、沙箱静默降级 |

### 1.4 run_python 的定位：能力缺口兜底

**定位**：`run_python` 是补位工具，不是主力工具。Agent 处理任务时先看现有工具能不能完成；都不能时，才现场写一段 Python，放进沙箱执行，拿到结果后继续任务。

```
任务
 └─ 现有工具能完成？ ── 能 ──> 直接调用该工具（不进沙箱）
        │ 不能
        ▼
   写 Python ──> run_python ──> 成功：取结果，继续任务
        ▲              │
        │              └─ 失败：读错误，改代码重试（有连续失败提示）
        │
   要联网 / 要读写用户文件？──> 在调用里声明 needs，经批准后再执行
   缺第三方库？──> 先换用预置库实现；仍做不了就告知用户（按需装包后置，9.6）
```

#### 1.4.1 这个定位带来的设计重心

| 特点 | 含义 | 设计上的对应 |
|---|---|---|
| 代码是现场写的、一次性的、没人事先审过 | OS 边界必须扛住最坏情况，人工审批不能是唯一防线；人也很难从一段临时代码里真看出风险 | 默认等级下无论代码写什么都出不了沙箱；审批只管“升级项”（1.4.3） |
| 失败重试是常态 | 首次运行写错很常见，每次重试都耗一轮模型调用 | 启动开销要有预算（G6、15.1）；错误要让模型直接据此改代码（1.4.4）；连续失败有提示 |
| 依赖不可预知 | 模型会 `import` 任意第三方库 | 首版：**做厚预置依赖档**，沙箱不联网、不装包，与 Anthropic 托管工具的做法一致（2.4 第 1 条）；预置包名单写进工具说明，让模型不必探路。按需安装（`needs.packages`）**后置**，等审计里“缺依赖”失败占比高再做（9.6、15.1） |
| 联网需求常见 | 抓取页面、调接口 | 联网是可以申请的能力，不是只能靠静态配置（1.4.2、8.2） |
| 处理的往往是用户的文件 | 格式转换、清洗、统计 | 文件按需复制进沙箱，结果由宿主复制回工作区（7.2） |
| 结果要回到模型 | 模型要的是“答案”，不是日志 | 结果回传规范，大结果自动落文件只回摘要（1.4.4） |
| 缺口任务多是“算一下、转一下” | 多数不需要在代码里编排宿主工具 | 工具桥接降为次要需求（第 6 章）：默认关闭，按调用声明；P4 再做 |

#### 1.4.2 能力申请（`needs`）

沙箱基线很窄：没有网络，看不到宿主文件，只有预置依赖。Agent 需要更多时，不能自己放宽，只能在调用里**声明**；宿主校验、人批准，然后按批准的范围生成这一次调用的授权集合（`Profile`）。批准只对这一次调用有效。

| 申请项 | 含义 | 宿主校验 | 默认 |
|---|---|---|---|
| `needs.packages`（**后置，P5**，首版不提供） | 需要的第三方包（名称加版本约束） | 预置依赖档里已有的不算升级；其余走依赖准备（9.6），受 `deps.*` 的允许/拒绝名单约束 | 空 |
| `needs.network` | 需要访问的域名（可带端口） | 拒绝 `*`、`*.com` 这类过宽的通配符；受 `network.deniedDomains` 与解析地址检查约束（8.2） | 空 |
| `needs.read` | 需要读取的宿主文件或目录（工作区路径） | 先过路径守卫，再过 `needs.read` 专用的**读拒绝清单**（7.5）。注意现有守卫在读取时只拦 `.env*`，`.git/`、`.agent/`、`mcp.json` 只在写入时才拦（`path_guard.rs` 的 `protected()`），所以不能直接说“守卫已经拒绝”，读取要另列清单；以**复制**进 `inbox` 的方式提供，不挂载；目录递归复制时逐项校验（7.4 入站）；受数量与大小上限约束 | 空 |
| `needs.exports` | 要把哪些产物放回工作区：`{from: outbox 内路径, to: 工作区路径}` | 过路径守卫，再过写回专用的**写拒绝清单**（7.5，比守卫更宽：含 `.vscode/`、`.github/workflows/`、`*.pth` 等）；视为一次写入，要批准；落地时对目标不跟随符号链接（7.2）；沙箱本身从不直接写工作区 | 空 |
| `needs.bridge` | 需要在代码里调用的宿主工具 | 须在 `bridge.tools.allow` 内，且不是硬拒绝项（6.4） | 空 |

每一类申请能否提出、提出后是否询问人，由 `escalation.*` 配置决定（10.3）。申请超出配置允许的范围时，不弹审批，直接返回“不允许”，避免让人批准一个本来就不会生效的事。批准也不能越过各自的硬限制（拒绝列表、受保护路径、平台能力）。**批准范围**：批准只对这一次调用有效。后置的 `packages` 启用后是例外：按锁定哈希在当前进程内记住（理由与限制见 1.4.3）。

#### 1.4.3 审批：基线放行，升级询问

审批与沙箱是两件事（Codex 的设计同样如此）：沙箱限制代码**能做什么**，审批决定**要不要给更多**。

- **基线调用**：`needs` 为空（只用预置依赖档里的库）。代码只能在“空房间”里活动，最坏结果是这段代码在里面乱跑一阵。因此**建议默认自动执行**（`approval.baseline = auto`），不让人逐段审代码，否则每个缺口任务都要打断一次。前提是启动自检通过、隔离确实生效（R8）；`level=off` 或降级后端时，一律询问。
- **升级调用**：`needs` 里有升级项。审批提示展示代码全文，加逐项申请（连哪些域名、读哪些文件、写到哪里；启用按需安装后还有装哪些包）。批准仅对这一次有效，不跨调用保留。
- 外层 `run_python` 调用的审批发生在沙箱启动**之前**，所以沿用现有的挂起/恢复机制没有问题（现有 `WhenUnanswered` 默认就是 `Suspend`）。只有沙箱运行期间由代码发出的嵌套桥接调用才不能挂起（4.3）。要区分两种“没人回答”：暂时没人答（前端还在，只是没来得及答）走挂起，等人回来再恢复；根本没有前端（批处理、定时任务）才直接拒绝升级项（8.1、10.3）。

与现有审批机制的衔接（代码事实）：

- `DualApprovalCallback` 已有 `ApprovalRule::When(predicate)`：谓词只在**整体参数**能解析成 JSON 对象时才生效，参数为空、解析失败或不是对象时**强制询问**（`dual_approval.rs` 的 `unreadable_arguments`）。`run_python` 可以注册为“`needs` 里有升级项就询问”。注意这层 fail-closed 只覆盖整体参数；`needs` 内部的形状错误或未知键不在其内，要靠下面“谓词与工具同源解析”那条补上。
- 已有 `without_standing_approval`：“总是允许”只批准当次，不会被记住。`run_python` 应该配置它，否则一次“总是允许”就等于以后的所有升级申请都放行。
- CLI 的 `--dangerous-tools` 只能按工具名整体开关，表达不了“基线放行、升级询问”。CLI 需要为 `run_python` 单独注册规则。
- 谓词只检查 `needs` 是否声明了升级项，**不检查代码内容**。这是有意的：代码里写了 `requests.get(...)` 却没声明联网，沙箱里就是连不上，错误会提示模型去申请。安全性来自 OS，不来自对代码的静态判断。
- 启用按需安装后，谓词判断“是否预置包”需要预置包清单，构造审批规则时传入。首版没有 `packages`，谓词只看 `network`、`read`、`exports`、`bridge` 是否非空。
- **谓词与工具同源解析**：谓词和 `NeedsResolver` 用同一个解析函数判断“是否含升级项”，不各写一份。解析函数把下列情况一律判为升级项（即询问），而不是忽略：`needs` 不是对象、字段类型不符、出现未知键、同一项重复出现。工具侧再做一道：凡是谓词没判为升级项的调用，`NeedsResolver` 只授予基线，不授予任何 `needs`。这样谓词与工具对同一份参数不会有两种理解，“谓词放行、工具却授权了”的缝隙不存在。
- **隔离状态如何传给谓词**：`ApprovalRule::when` 的谓词是同步的，只拿到 `ToolCallView`，拿不到 `ExecutionContext`，也等不了异步结果。所以“隔离已确认生效”不能在谓词里现场探测。做法：启动自检在构造 `RunPythonTool` 时（或首次使用前）完成，结果放进共享的原子状态（例如 `Arc<AtomicU8>` 表示“已确认 / 降级 / 未确认”），谓词只读它；运行中发现隔离失效（后端被撤销、复测失败）就翻转，之后的基线调用都回到询问。自检结果按（后端、profile 形状）缓存，不是每次调用都重做（第 14 章“启动自检”同）。
- **审批内容要按工具渲染**：现有提示直接打印原始参数 JSON（终端是 `eprintln!("参数: {}", raw_arguments)`，Web 端待审批快照里的 `raw_arguments` 同样是原始串，见 `dual_approval.rs` 的 `PendingApproval`），代码会变成一行带转义的字符串，人读不了。所以“展示代码全文、逐项展示 `needs`”不是现成能力，需要 `run_python` 提供自己的渲染：代码按行展示，`reason` 转义后用等宽纯文本，`needs` 逐项分行（组合风险的提示见 R18）。终端与 Web 两端都要接。这是 R19 缓解措施的前提，列入 P1（15.1）。
- **工具侧默认只允许基线（fail-closed）**：审批是工具之外的回调，工具自己不弹审批。因此 `RunPythonTool` 构造时的授权上限**默认只有基线**；只有调用方显式声明才会抬高到配置的等级，声明只有两种：(a) 升级项的审批规则已接线（CLI 注册 `ApprovalRule::When` 规则时一并声明）；(b) 调用方明确选择免审批（对应 CLI 的 `--no-approval`，横幅明示，见 3.3）。库使用者只注册了工具、没配审批规则时，两者都不成立，`needs` 不会生效，调用会收到“本部署未接入审批，升级项不可用”。
- **重试时的重复询问**：代码出错后改了再跑，是兜底场景的常态。首版的升级项（`network`、`read`、`exports`、`bridge`）每次调用都重新询问：它们的范围每次可能不同，且涉及外泄与写入。以下是后置的 `packages` 启用后的处理：如果每次重试都重新弹一遍装包审批，体验会很差，折中是 `needs.packages` 的批准按**锁定哈希、在当前进程内**记住（批准的是“这组包、这个来源、这些文件哈希”，内容由哈希锁定，不会随调用改变，所以记住不扩大授权）。实现上要注意：`ApprovalRule::When` 的谓词只拿得到当次调用的视图（`ToolCallView`），拿不到 `ExecutionContext`，所以它无法按对话区分，只能靠谓词闭包捕获的进程内共享状态判断“这份锁定是否批准过”。如果需要按对话记住，要改写成自定义的 `BeforeToolCallback`（它能拿到上下文）。这份状态不随挂起的运行落盘，进程重启后会重新询问（安全方向的失败）。

#### 1.4.4 结果回传与错误反馈

结果有三路：

1. **返回值**：代码调用 `set_result(obj)`，这是“答案”，必须能转成 JSON。
2. **文本输出**：stdout 与 stderr，首尾保留、中间截断（沿用 `Capped`）。
3. **文件产物**：`outbox` 里的文件，只回传清单（名称、大小、sha256、简短预览），内容不自动进入上下文。

规则：

- **大结果自动落盘**：返回值序列化后超过 `limits.maxResultBytes`，不塞进上下文，自动写成 `outbox` 里的文件，回传摘要（类型、长度、前几项或字段预览）和路径，并提示模型“用代码再处理，不要整个读回来”。
- **不可序列化的对象**（表格、数组、字节串等）：SDK 按类型给出明确的摘要或转换，无法转换就报错并提示改成可序列化的形式。不静默丢数据。
- **未调用 `set_result`**：只回传文本输出，不去猜“最后一个表达式”是不是答案。

错误按类别回传，每类给模型明确的下一步：

| 类别 | 回给模型的内容 | 下一步提示 |
|---|---|---|
| 代码异常 | 异常类型、消息，以及**只含用户代码帧**的 traceback（去掉 SDK 帧，会话路径替换成 `<work>`） | 直接改代码重试 |
| 缺依赖 | 识别 `ModuleNotFoundError`，转成结构化提示“包 X 不在预置依赖中”，并附预置包名单的位置 | 首版：改用预置库实现；确实做不了就告知用户。启用按需安装后：可在 `needs.packages` 申请 |
| 被沙箱拒绝 | 文件或网络访问被 OS 拒绝时，转成“被沙箱拒绝：此访问需要在 `needs` 申请 X”，不展示宿主无关路径 | 申请能力，或换办法 |
| 超时或资源 | 注明是被超时或内存上限终止，附终止前的输出 | 减少数据量、分批处理 |
| 后端不可用 | 缺什么、怎么处理（写给用户看） | 不要重试，转告用户 |
| 申请被拒 | 用户的拒绝及理由 | 换方案或询问用户 |

**连续失败提示**：同一轮任务里 `run_python` 连续失败达到 `retry.maxConsecutiveFailures`（默认 5）次，在结果后追加一句“已连续失败 N 次，请换思路或向用户确认”。它是提示，不是硬拦截：硬拦会让任务直接死掉。可以由 `AfterToolCallback` 根据对话记录统计实现（该回调拿得到 `ExecutionContext`），不需要工具自己保存状态。

#### 1.4.5 引导模型正确使用

- **工具说明**要写明三件事：仅当现有工具做不了时才用，优先用现有工具；结果用 `set_result` 返回；沙箱默认没有网络、看不到宿主文件，需要时在 `needs` 里申请。
- **环境清单**写进工具说明：Python 版本、预置包名单、时间与内存上限、当前网络状态。首版不能装包，预置包名单就是模型能用的全部库，必须写全（只列包名，不列版本和说明，控制长度）。这样模型不用先花几轮去探路；社区实践文章也建议把“无网络、无文件系统、无跨调用状态”这类限制直接写进工具说明（2.4 第 8 条）。注意（代码事实）：`ToolRegistry::add` 在注册那一刻取一次工具定义，所以清单在注册时定格，运行中变化（例如部署的联网上限被改，或启用按需安装后新增了包）不会反映到工具说明里；需要时另提供只读的 `python_env` 查询（P5，见 15.1）。
- **两个执行环境不共享状态**：Anthropic 的文档提醒，同时提供两个执行环境（托管沙箱加客户端 Bash）时，模型可能用错工具，或误以为它们共享状态。本方案同样有两个：`run_python` 在沙箱的工作目录里运行，`run_command` 在宿主的工作区里运行，二者的文件和变量互不可见。两个工具的说明里都要写明，数据要在二者之间传递时，只能经 `needs.read`、`needs.exports`。
- **旁路风险**：模型手里还有 `run_command` 时，可以直接 `python script.py` 绕过沙箱。只要 `run_command` 不隔离，`run_python` 的边界就能被模型“选另一条路”绕开。但 `run_command` 要用宿主工具链（`cargo`、`git` 等），不能直接套用默认沙箱，所以没有一个零代价的修法：首版靠审批把关加引导（工具说明优先 `run_python`，审批提示里对解释器命令加醒目警告），这是**已知的残余风险**；分级隔离留到后续（R16，15.2 第 3 项）。

| Pyodide 加 Deno（WASM 路线，实践文章 2026-09-11） | Pyodide 是编译成 WASM 的 CPython，Deno 默认拒绝文件、网络、环境变量、子进程。文章的论点：**增量式**（从零权限起步，失败时倾向关闭）比**减法式**（容器从无所不能起步，靠配置逐项剥夺，失败时倾向开放）更稳。限制：不支持 psycopg2、torch 等原生扩展和 `multiprocessing`；作者称比原生 CPython 慢 1 至 3 倍（无基准）；WASM 无法抢占死循环，要靠外层进程设墙钟超时并杀进程。推荐 WASM 为默认、容器按需、高安全时两层叠加。`langchain-sandbox`（基于 Pyodide 加 Deno）的 README 称已不再维护，不建议生产使用（**【摘要级】**，来自搜索摘要） | “增量式更稳”的论点同样适用于本方案：基线是空房间、能力逐项申请，正是增量式。但它的库兼容限制对补位任务是硬伤，所以只作后续的强隔离补充（2.2） | 【已核实】文章；维护状态为【摘要级】 |
| CodeAct 与 OpenHands | CodeAct（2024 年 2 月，Xingyao Wang 等）主张把动作写成可执行的 Python 而不是 JSON 工具调用；OpenHands 为每个 agent 提供独立的 Docker 运行环境。二手综述称，代码执行失败后的具体报错（如 `TypeError`）比模糊的“工具调用失败”更利于模型自我修复 | 支持 1.4.4 的“错误要具体、只含用户代码帧的 traceback”。论文原文**未读**，不引用其具体数据 | 【摘要级】，均为二手资料 |

### 2.2 隔离技术路线对比

| 路线 | 隔离强度 | 跨平台且零安装 | 启动开销 | 原生库兼容 | 运维成本 | 结论 |
|---|---|---|---|---|---|---|
| 进程级 OS 沙箱（Seatbelt / Landlock+bwrap / AppContainer） | 中（共享内核） | 好 | 毫秒级 | 完整 | 低 | **默认选择** |
| 容器（Docker、rootless podman） | 中高 | 差：Windows 与 macOS 要虚拟机，且需要守护进程 | 百毫秒至秒级 | 完整 | 中 | 作为可插拔后端，面向服务端部署 |
| gVisor、Firecracker 等 microVM | 高 | 差：需要 Linux 与 KVM | 秒级以内 | 完整 | 高 | 多租户场景的可选后端（背景知识，未联网核实） |
| WASM（Pyodide 加 Deno） | 高（增量式能力模型，失败倾向关闭） | 很好（要带一个 Deno 运行时） | 秒级（Monty 作者给的数字是 Pyodide 约 2.8 秒，非独立测量） | 受限：不支持 psycopg2、torch 等原生扩展和 `multiprocessing`；比原生慢（作者称 1 至 3 倍，无基准）；无法抢占死循环，要外层进程超时 | 中 | 不作默认；可作后续的“强隔离轻量档”，或与 OS 沙箱叠加。`langchain-sandbox` 已不再维护（【摘要级】） |
| 受限解释器（Pydantic Monty 这类，Rust 自研） | 高（只能经宿主提供的函数交互），但项目早期，无正式审计 | 很好（纯 Rust，可嵌入） | 微秒级（作者数据） | **差：不是 CPython，不支持第三方库**，标准库也只有一小部分 | 低 | 不适合补位任务；可关注，用于“只编排宿主工具”的纯胶水场景 |
| 语言层限制（RestrictedPython、audit hook、smolagents 的 `LocalPythonExecutor`） | 低，可绕过 | 好 | 极低 | 受限 | 低 | 不作为边界，只作辅助加固。smolagents 官方文档也明确说它不是真正的沙箱 |

### 2.3 选型结论与关键取舍

| 决策 | 选择 | 理由 | 代价 |
|---|---|---|---|
| D1 隔离层级 | 进程级 OS 沙箱 | 与项目“本地 CLI 为主”的定位匹配，三平台都能零依赖运行 | 共享内核，强度低于 VM；用后端抽象为以后留出口 |
| D2 实现方式 | 自有薄后端层，不引入 `birdcage` | `birdcage` 已归档、GPL、无 Windows | 需要自己维护 Seatbelt profile、Landlock/seccomp 规则、Windows 令牌代码 |
| D3 应用沙箱的时机 | **辅助进程（helper）模式**：宿主启动本程序的 helper 入口，由它在单线程环境下完成加固，再 `exec` Python | 宿主是多线程 tokio 运行时，fork 之后到 `exec` 之前只允许异步信号安全的操作；Landlock、seccomp 的规则构造需要内存分配，放在 `pre_exec` 里不安全。（这条是推断，**【待验证】**：规则集可以在 fork 之前构建好，`pre_exec` 里只剩 `prctl`、`landlock_restrict_self`、`seccomp` 这类系统调用，是否可行要在 P0 的 PoC 里确认；bwrap 自带 `--seccomp FD`，也是备选，同属背景知识，未核实） | 多一次 exec；Windows 不需要 helper（令牌在创建进程时设置）。**对库使用者的落地方式未定**：本 crate 同时是库和 CLI，“本程序的 helper 入口”在库使用者自己的二进制里不存在。三个选项：独立的 helper 二进制（随发行包分发）、`arg0` 分发（使用者要在 `main` 首行调用一个入口函数）、或上面的 `pre_exec`。见 15.2 第 12 项 |
| D4 通信通道 | 继承的双工流上的 JSON-RPC，不用 TCP 或 Unix socket 路径 | AppContainer 默认阻断回环；Seatbelt、Landlock 下不需要为通信放开任何路径或端口；子进程拿到句柄即是身份，不需要令牌 | Windows 需要自定义进程创建；Python 侧要写一个小 SDK |
| D5 读取策略 | 默认**白名单读取**（只可见运行时、SDK、skill、工作区目录和必要的系统库），可配成黑名单读取 | “默认受限访问”的字面要求；`sandbox-runtime` 默认是黑名单读取，兼容性更好但默认暴露面更大 | macOS 上要维护系统库白名单，容易漏项导致解释器无法启动 |
| D6 路径语义 | 三个平台统一使用**真实宿主路径**（对话工作目录与本次运行目录），不做虚拟的 `/sandbox/...` 路径 | macOS 与 Windows 没有 bind mount；统一语义胜过好看的路径 | 沙箱内能看到宿主目录结构的一小部分，通过环境变量与 SDK 常量告知路径 |
| D7 桥接策略 | 桥接降为次要路径：默认关闭，按调用在 `needs.bridge` 声明才可用；嵌套调用走与直接调用相同的策略链，`Suspend` 视为拒绝 | 缺口任务多是“算一下、转一下”，不需要在代码里编排宿主工具；桥接是特权升级面，不该默认开着。不创造第二套权限体系；活进程无法挂起恢复 | 需要预先在 `needs.bridge` 声明用到的工具，否则交互审批会拖慢长任务；批处理省 token 的收益要显式开启才有。“声明即预批”只允许预批 6.4 里“纯计算、本地只读”两类；写入类只能逐次审批（无人值守即拒绝）或不开放，否则预批就成了对任意参数的常驻批准（4.3） |
| D8 Python 运行时与依赖 | 受管的独立 Python，加**做厚的只读预置依赖档**；沙箱内不联网、不运行 pip。按需安装（宿主侧下载、校验后只读挂载，9.6）作为**后置能力**，有数据支持再做 | Anthropic 托管工具同样不允许装包，靠预装库覆盖常见任务（2.4 第 1 条）；预置档能避免首版就背上依赖解析、下载、供应链审查这一整块复杂度；让沙箱自己联网装包又会把网络权限放得太宽 | 预置档以外的库一律用不了，会有一部分任务失败，要靠审计数据判断占比；预置档要有人维护，体积会变大 |
| D9 审批模型 | 基线调用自动执行，升级调用（`needs` 里有升级项）逐次询问；沙箱管“能做什么”，审批管“要不要给更多” | 一次性代码很难靠人读出风险，让人逐段审代码会把兜底工具变成打断工具；OS 边界已经限定了基线的最坏结果 | 依赖隔离确实生效；`level=off` 或降级后端时必须回到逐次询问；需要给 CLI 增加按参数判断的规则（1.4.3） |
| D10 能力申请 | 通过调用参数 `needs` 声明，宿主校验后生成本次调用的授权集合，批准只对当次有效 | 让 Agent 自助解决“要联网、要读文件、要写回结果”，同时不让它自己放宽边界 | 多一套申请与校验逻辑；申请项要有明确的硬限制 |

本方案属于“代码作为临时补位工具”这一类，最接近的参照是 Anthropic 的 code execution tool 与 Claude Code 的沙箱。下表逐条列出读过一手资料后得到的启示，以及本方案的处理。“已采纳”表示设计里本来就是这样，社区实践是佐证；“备选”表示有价值但不进首版；“不采纳”给出理由。

|---|---|---|---|

| 9 | **审批与运行中的代码**：Cloudflare 用“中止并重放”（批准后用相同源码重放，已执行的调用返回记录的结果）；Monty 用 KB 级快照暂停与恢复 | Cloudflare 文档、Monty 文章 | **备选**：首版桥接维持“`Suspend` 视为拒绝”（4.3）。P4 做桥接时评估“中止并重放”。Cloudflare 的约束是：代码要确定性（同一序号上的调用必须与上次一致，否则报重放偏离）、非确定性来源要包进 `step`、可能暂停的执行要顺序发起调用，并且要有持久化的执行日志来保存已执行调用的结果。（推断，**【待验证】**）对本方案还意味着 Python 代码会从头再跑一遍，沙箱里的本地副作用（写文件等）会重复，重放时需要干净的工作目录。Monty 的快照依赖它自己的解释器，不适用于 CPython |

| 12 | **语言层限制不是边界** | smolagents 官方文档 | 已采纳（N4） |
| 13 | **WASM 无法抢占死循环，要靠外层进程超时** | 实践文章 | 不受影响：本方案是原生进程，宿主定时器杀整棵进程树（4.4） |
| 14 | **受限解释器（Monty）适合编排宿主函数，不适合要第三方库的任务** | Monty 文章 | **不采纳为主路径**：补位任务要 xlsx、PDF 等库，Monty 明确不会支持第三方包。可关注，用于纯胶水场景 |
| 15 | **“只沙箱化代码片段”与“整个 agent 放进沙箱”是两种架构**，前者简单但沙箱里拿不到模型凭据 | smolagents 文档 | 本方案属于前者：模型调用始终在宿主，沙箱里不放模型凭据。子 agent 类工具默认也不开放桥接，但那是另一个原因（代码循环调用会放大成本，见 6.4） |

**社区资料没有回答、需要我们自己验证的问题**（本次检索没有找到公开数据）：

- 补位式代码工具的成功率、平均重试次数、最常见的失败类别。所以 13 章要求记录这些指标，并用它来决定 `needs.packages` 要不要做、预置档要加什么。
- OS 级沙箱在 Windows 上的成熟开源实践。Anthropic 自己的 Windows 支持是 alpha，且需要一次性管理员安装；AppContainer 加 Job Object 的路线没有找到成熟的开源参照，所以 P3 要先做 PoC（9.4）。
- 基线自动执行在真实使用中的滥用情况。没有公开数据，只能靠自己的审计日志（13 章）观察。

### 3.2 组件职责

| 组件 | 位置 | 职责 | 不负责 |
|---|---|---|---|
| `RunPythonTool` | 宿主，`src/tools/python/`（新增） | 对模型暴露的工具；解析参数；驱动一次执行；汇总结果（输出、返回值、产物、桥接摘要、资源用量）；持有授权上限，**默认只有基线**，调用方声明审批已接线或明确免审批后才抬高（1.4.3 末条） | 不做审批（审批由策略链完成），不直接碰 OS |
| `SandboxManager` | 宿主，`src/sandbox/`（新增，`sandbox` feature） | 会话表与生命周期；配额；选择后端；构造 `Profile`；回收（杀进程树、删目录、撤销授权） | 不理解 RPC 业务 |
| `SandboxBackend`（trait） | 宿主 | `probe()` 探测可用性与实际能力；`spawn(profile, channel)` 返回子进程句柄；`kill_tree()`；`describe()` 给出隔离类型字符串，供启动横幅显示 | 不做策略决策 |
| 平台后端 | 宿主 | Seatbelt 后端、bwrap+Landlock+seccomp 后端、AppContainer+Job 后端；未来的容器后端 | - |
| `Profile` | 数据结构 | 把配置编译成与平台无关的授权集合：只读路径、可写路径、拒绝路径、网络模式、资源上限、环境变量白名单 | - |
| `Channel` | 宿主 | 抽象“带长度前缀的双工字节流”；Unix 为 `socketpair`，Windows 为命名管道 | - |
| `BridgeDispatcher` | 宿主 | 处理沙箱发来的 `tools.*`、`skills.*`；白名单、限速、预算、审计；经策略链执行 | 不信任沙箱传来的任何内容 |
| `SkillRegistry` | 宿主 | 发现并校验 skill 目录；提供只读挂载清单；登记宿主侧 skill 工具 | - |
| `ArtifactHarvester` | 宿主 | 从 `outbox` 回收产物并校验（7.4）；执行 `needs.exports` 的导出 | - |
| `NeedsResolver` | 宿主 | 校验 `run_python` 的 `needs`，与配置的允许范围求交，得出这次调用的授权集合；判断是否含升级项（供审批规则使用，**与审批谓词共用同一个解析函数**，未知键与形状不符一律判为升级项，1.4.3）；谓词没判为升级项的调用只授予基线；超出允许范围时直接拒绝 | 不弹审批（审批由策略链完成） |
| `DependencyBroker`（**后置，P5**） | 宿主，`sandbox` feature | 按需准备第三方包：解析、下载、校验、构建只读环境层并缓存（9.6）；`packages` 申请的唯一执行者 | 沙箱内的代码无权触发它，只能通过 `needs.packages` 间接请求。首版不实现 |
| `sandbox_sdk` | 沙箱内（Python 包，随宿主版本分发） | RPC 客户端；工具与 skill 的存根；`inputs`、`emit`、`publish` 等接口 | 不是安全边界，代码可以绕过它直接说协议 |
| 受管运行时与环境 | 数据目录 | 只读的 Python 解释器与预置依赖 | - |

### 3.3 与现有代码的集成点

- **工具注册**：`run_python` 作为新工具加入 `ToolRegistry`，不进 `builtin()`（与 `run_command` 的处理一致），只在 `builtin_all()` 与 `select()` 中提供。
- **路径守卫要扩展**（代码事实）：`WorkspaceGuardCallback` 目前只读取参数里**顶层的字符串字段**（`arguments.get(field).as_str()`），字段缺失或不是字符串时直接跳过，交给工具自己报错。而 `needs.read[]`、`needs.exports[].to` 是嵌套数组里的路径，现有机制看不到，放着不管等于放行。所以需要：(1) 让守卫支持嵌套与数组路径；(2) 对 `run_python` 这类字段，形状不符（不是预期的字符串或数组）按拒绝处理，而不是跳过；(3) `NeedsResolver` 在工具内部再按工作区根目录校验一遍，作为第二层。另外，守卫里有一个回归测试，要求每个内置工具要么登记在 `guarded_fields`，要么列入“不涉及路径”的名单；`run_python` 登记进去，这条测试就同时成为“新工具不会漏过守卫”的验收。
- **每个路径字段要标明命名空间与校验方**：守卫把相对路径按**工作区根**解析（`path_guard.rs` 的 `violation()`），所以只有工作区路径的字段才能登记进去，沙箱内路径不能。误把沙箱内路径登记给守卫，会按工作区解析出错误结论。
  - `needs.read[]`：工作区路径；守卫（需扩展到数组）加读拒绝清单（7.5）；`NeedsResolver` 复核。
  - `needs.exports[].to`：工作区路径；守卫（需扩展到嵌套）加写拒绝清单（7.5）；`NeedsResolver` 复核。
  - `needs.exports[].from`：`outbox` 内路径；不是工作区路径，**不登记进守卫**；由 `ArtifactHarvester` 按 7.4 出站规则校验。
  - `script`：对话 `work` 目录或只读 skill 挂载内的路径；同样不是工作区路径，**不登记进守卫**；由 `RunPythonTool` 按“必须落在这两处之内、不跟随符号链接”校验。
  - 守卫的回归测试因此要给 `run_python` 登记 `needs.read[]`、`needs.exports[].to` 两个字段，并在测试里注明另外两个字段不登记的理由。
- **审批**：按 1.4.3：用 `ApprovalRule::When` 实现“有升级项才询问”，并配置 `without_standing_approval`；谓词与 `NeedsResolver` 共用解析函数，审批内容要按工具渲染（现有提示只打印原始 JSON）。CLI 的 `--dangerous-tools` 只能按工具名整体开关，所以 `run_python` 的规则要单独注册，并同时声明“审批已接线”（1.4.3 末条）。`--no-approval` 的语义保持不变：它会让升级项也不再询问，横幅需要明示；这是“调用方明确免审批”的唯一入口。
- **结果后处理**：连续失败提示用 `AfterToolCallback` 实现（该回调拿得到 `ExecutionContext`，可统计对话记录里 `run_python` 的最近结果），不需要工具保存状态。
- **旁路：`run_command`**：`run_command` 仍是不隔离的，模型可以用它直接跑 Python，绕过 `run_python` 的边界。它要用宿主工具链，不能直接套用默认沙箱，所以首版接受为已知残余风险，靠审批与引导缓解；分级隔离留到后续（1.4.5、R16、15.2 第 3 项）。`SandboxBackend` 与 `Profile` 与 Python 无关，是为这个后续留的口子。
- **嵌套调用拿上下文**：有两个选项，推荐 A。
  - A：运行时在执行工具期间设置一个 task-local 的“嵌套调用句柄”，与 `usage::charge` 的做法同构；桥接处理因此必须与 `run_python` 在同一任务内。不改 `Tool` trait，没有破坏性变更。
  - B：给 `Tool::execute` 增加上下文参数。`tool.rs` 的注释已经预留了这个口子（“如果有具体工具需要，就加回来”）。这是破坏性变更，但如果之后还有别的工具需要，一次改完更干净。
- **取消与超时**：沿用 `execute_with_timeout`；`run_python` 声明自己的超时（略大于内部上限，参考 `run_command` 的 610 秒做法）。丢弃 future 时，守卫对象负责杀进程树、关通道、清理目录。
- **并发**：`concurrency_safe()` 返回 `false`；同一会话内的执行串行。另设全局并发沙箱数上限（`session.maxConcurrentSandboxes`，默认 2），避免一轮里并行调用几个 `run_python` 把机器拖垮。
- **取得会话标识**：工作目录按对话保留（4.5）需要 `ExecutionContext.conversation_id`，而 `Tool::execute` 拿不到它。与嵌套调用一样，用 task-local 或扩展 `Tool` 解决，二者合用同一机制。
- **CLI 横幅与开关**：现有 `--no-sandbox` 只关路径守卫，新的 OS 隔离需要另起名字（暂定 `--isolation <off|read|write|net>`）。横幅分别显示“守卫：开/关”和“隔离：seatbelt、landlock+bwrap、appcontainer 或 none”。两者互不影响：`--no-sandbox` 不得关闭 OS 隔离，`--isolation off` 也不得关闭守卫。
- **可复用性**：`SandboxBackend` 与 `Profile` 与 Python 无关。以后 `run_command` 可以在 `build()` 之后、`spawn()` 之前套用同一后端（此前的计划），本文不展开。

### 3.4 信任域

```
可信:    host process, SandboxManager, BridgeDispatcher, SkillRegistry, ArtifactHarvester
半可信:  受管运行时与依赖(只读, 由宿主构建并校验哈希)
不可信:  沙箱内全部进程, 含 sandbox_sdk, 含 skill 脚本, 含 outbox 里的一切文件内容
```

## 4. 沙箱生命周期与交互流程

### 4.1 启动

1. `RunPythonTool` 收到参数，先经策略链（路径守卫、审批；审批规则见 1.4.3）。通过后才会创建任何沙箱资源。
2. `NeedsResolver` 校验 `needs`，与配置求交，并与工具持有的授权上限求交（上限默认只有基线，见 1.4.3 末条）。超出允许范围直接返回“不允许”，不继续。
3. `SandboxManager` 解析配置，得到有效的 `Profile`（项目级配置只能收紧，见 10.2），再叠加这次调用被批准的 `needs`。
4. 后端 `probe()`：确认内核特性、命名空间、令牌与 ACL 授权等是否真的生效。不满足且未允许降级则直接报错，错误里写明缺什么。
5. （后置，P5）有 `needs.packages` 时，`DependencyBroker` 准备依赖环境层（命中缓存则跳过）；失败直接返回，不启动沙箱。首版跳过这一步。
6. 取得（或创建）本对话的工作目录（`work`、`tmp`、`inbox`、`outbox`；目录名取对话键的哈希，4.5），把 `needs.read` 里的宿主文件按 7.4“入站”规则逐项校验后复制进 `inbox`。
7. 建通道；构造 helper 的启动规格（授权集合、资源上限、环境变量），通过一个独立的继承 fd 传给 helper。
8. helper 完成加固（`no_new_privs`、资源上限、Landlock、seccomp、Seatbelt），`exec` Python（隔离模式）。Windows 由宿主直接以 AppContainer 令牌和 Job Object 创建进程。
9. 握手：沙箱 SDK 发 `session.hello`，宿主校验协议版本和工具目录摘要。超时则杀掉。
10. 握手完成，才发送 `exec.run`。

以上是通道就绪后（P1 起）的完整流程。P0a/P0b 还没有通道（15.1）：第 7 步里“建通道”的部分和第 9、10 步省略，代码与输入由宿主直接交给解释器（具体方式在 P0a 里定），返回值经运行目录里的结果文件取回，该文件的读取同样必须按 7.4 出站规则校验（不跟随符号链接、只接受普通文件、限制大小），不能因为“过渡做法”就放宽。

### 4.2 一次执行

```
Agent        RunPythonTool       Manager/Broker/Bridge       Sandbox(Python+SDK)
  | run_python(reason,code,needs) |                              |
  |----------------->| policy chain: guard -> approval (only if needs has escalations)
  |                  | NeedsResolver: validate needs, intersect with config
  |                  | DependencyBroker: prepare packages (deferred to P5, skipped in the first release)
  |                  | copy needs.read -> inbox
  |                  |--spawn-------->|----exec Python-------------->|
  |                  |<-------------- session.hello -----------------|
  |                  |--exec.run(code, inputs)--------------------->|
  |                  |<-- emit(progress/log) ... (notifications) ----|
  |                  |<-- net.fetch(...)      (only if needs.network, brokered) --|
  |                  |<-- tools.call(...)     (only if needs.bridge) ------------|
  |                  |    host: allowlist -> policy chain -> execute -> result --->|
  |                  |<-- exec.run result(status, set_result value) -|
  |                  | harvest outbox, apply needs.exports (guarded), capture stdout/stderr, usage
  |<-- tool result --|  (classified status + hints; large result -> file + summary)
```

### 4.3 带审批的嵌套调用（仅桥接开启时）

桥接默认关闭（D7），只有调用声明了 `needs.bridge` 才会发生下面的流程。

1. 沙箱发 `tools.call(write_file, ...)`。
2. 白名单判定。不在 `needs.bridge` 声明的范围内，直接返回 `PolicyDenied`，不打扰人。
3. 在范围内：构造“嵌套调用视图”，调用 ID 形如 `<父调用ID>/<序号>`，进入同一条 `BeforeToolCallback` 链。
4. 链返回 `Suspend`（比如审批没有及时回复）时，按拒绝处理，返回 `ApprovalTimeout`。原因：Python 进程活着，不能落盘后恢复。
5. 审批提示里要展示父调用（哪段代码）、嵌套调用及参数，以及“该批准在本次执行内有效”的范围。**“总是允许”不跨执行保留**。
6. 推荐的主路径是**声明即预批**：`needs.bridge` 在审批外层 `run_python` 时一并批准，执行期间不再逐个询问。外层审批发生在沙箱启动之前，可以正常挂起与恢复（1.4.3）。**预批的范围要收窄**：预批等于对被声明工具的任意参数做一次性批准，与 `without_standing_approval` 的原则相悖（现有实现的注释说得很清楚：对 shell 类工具，一次“是”就是对任意命令的“是”）。所以 `bridge.approval.mode=manifest` 只能预批 6.4 里“纯计算”和“本地只读”两类；“写入或破坏”类即使在 `bridge.tools.allow` 里，也只能 `each`（逐次审批，沙箱运行期间遇到 `Suspend` 按拒绝）；无人值守时一律拒绝。
7. **备选：中止并重放**（P4 评估，不进首版）。Cloudflare Code Mode 不挂起运行中的代码，而是在遇到需审批的调用时中止这一轮，批准后用相同源码重放，已执行的调用直接返回记录的结果（2.4 第 9 条）。如果采用，需要：持久化的执行日志、确定性的代码（同一序号上的调用与上次一致）、顺序发起调用，以及重放时干净的工作目录（后一条是推断，**【待验证】**）。采用后，“`Suspend` 视为拒绝”这条限制可以放宽成“可暂停”，代价是代码写法受约束，且每次重放都要重新启动沙箱。

### 4.4 取消、超时与崩溃

| 事件 | 处理 |
|---|---|
| 超时（墙钟） | 宿主先发 `exec.cancel`，等待 `cancelGraceMs`；未退出就杀整棵进程树。返回已捕获的输出（与 `run_command` 的行为一致） |
| 上层取消（future 被丢弃） | 守卫对象 Drop：杀进程树、关通道、清理目录 |
| 宿主崩溃 | 子进程自行退出：Linux 用父进程死亡信号；Windows 靠 Job 的 kill-on-close；通道 EOF 时 SDK 主动退出。macOS 无父进程死亡信号，靠 EOF 加看门狗（**【待验证】**） |
| 沙箱崩溃或 OOM | 通道 EOF；宿主记录退出原因和资源用量，把“被资源限制杀掉”和“代码异常”区分开 |
| 协议违规（超大帧、乱序、洪泛） | 立即关通道并杀进程；记审计 |
| 清理不彻底（进程逃出进程组） | Linux：PID 命名空间或 cgroup 兜底；Windows：Job；macOS：杀进程组后再按父子关系扫描一遍，已知有残余风险（12 章） |

### 4.5 会话与状态

兜底场景里典型的是“写、跑、看结果、改”的短循环，同一个对话里会连着调用多次。所以把“进程”和“文件”拆开处理：

- **进程：每次调用一个新的，结束即销毁（默认，也是首版唯一的模式）**。无状态，最安全，也最简单。代价是每次都要重新加载数据；对兜底任务可以接受，需要复用的中间数据写文件即可。
- **文件：工作目录按对话保留（默认）**。同一个对话的多次调用共用同一个 `work` 目录，第一次写的辅助脚本、缓存的中间文件，第二次还在。`tmp`、`inbox`、`outbox` 每次调用重建。一次性对话（没有 `conversation_id`）按单次调用处理。
  - **目录键用哈希，不用原始 id**：`conversation_id` 是调用方给的任意字符串（`ExecutionContext` 里是 `Option<String>`），并且有 `conversation_scope` 命名空间。直接拿它做目录名会有路径穿越和跨 scope 碰撞的风险。键取 `ExecutionContext::continuity_key()`（已折入 scope，用 NUL 分隔防歧义）的哈希（例如 SHA-256 的十六进制前缀），原始 id 不出现在路径里。
  - **清理靠空闲扫描和容量上限，不靠“对话结束”**：库里没有“对话结束”事件（现有 `DualApprovalCallback` 的注释也明说回调不会被告知一次运行何时结束，所以它的记忆用有界缓存）。所以清理只有两条：空闲超过 `session.workIdleTimeoutSecs`，或对话目录总数、总大小超过上限时按最久未用淘汰。工具说明里不要承诺文件长期保留。
- **持久解释器（可选，后续）**：同一个解释器跨调用保持变量，类似 Jupyter 内核（背景知识）。适合反复探索同一份大数据。实现代价高（状态不可序列化、与取消和超时交互、残留变量带来的不确定性），收益只在重复加载成本很高时才显现，所以放到后续阶段，并要在 `session.mode` 显式打开。
- **分离执行与 `python_send`/`python_poll`**：用于长时间运行并与程序对话，不是缺口兜底的典型场景，**移出路线图**，需要时另立项。

### 4.6 产物回收

执行结束或沙箱调用 `artifact.publish` 时，`ArtifactHarvester` 扫描 `outbox`，按 7.4 的规则校验，把通过的文件登记成产物（名称、大小、sha256、宿主路径）。结果文本里列出清单，文件内容**不自动进入模型上下文**。

## 5. 通信协议与接口边界

### 5.1 传输层

| 平台 | 载体 | 说明 |
|---|---|---|
| Linux、macOS | `socketpair(AF_UNIX, SOCK_STREAM)`，子进程继承一端（约定为 fd 3） | 单个双向 fd；不涉及文件系统路径，也不涉及网络端口。`pre_exec`/helper 负责保证只继承这一个额外 fd |
| Windows | 宿主创建命名管道服务端，客户端句柄设为可继承，用句柄列表属性只传给子进程；句柄值通过环境变量告知 | AppContainer 默认阻断回环，不能用 TCP；继承的句柄在使用时不再做访问检查，所以不必为管道设置面向 AppContainer 的 ACL（**【待验证】**） |

两条规则：stdout、stderr 只用来承载用户代码的输出，宿主按原有的 `Capped` 方式捕获，**不复用来传协议**（`print()` 会污染它）；stdin 关闭。

对端身份靠“持有继承来的句柄”表达，不需要令牌。宿主仍把对端当作不可信输入处理。

### 5.2 帧与消息

- 帧：4 字节大端长度加 UTF-8 JSON。长度先于缓冲检查，超过 `ipc.maxFrameBytes` 即视为违规。
- 消息：JSON-RPC 2.0，请求、响应、通知三种。ID 前缀区分发起方（宿主 `h-`、沙箱 `s-`），避免冲突。
- 只用 JSON，不用 pickle 或其他可执行语义的序列化。JSON 解析限制嵌套深度和字符串长度。
- `_meta` 字段携带 `execId` 与 trace 上下文，用于接上现有的 `execute_tool` span。
- 二进制数据不进帧：小的用 base64（受 `ipc.inlineMaxBytes` 限制），大的走目录交换（7.2）。

### 5.3 方法表

宿主到沙箱：

| 方法 | 类型 | 参数 | 说明 |
|---|---|---|---|
| `session.hello` | 请求（由沙箱先发出，宿主应答） | 协议版本、会话 ID、SDK 版本 | 握手；宿主在应答里下发有效限制、可用工具目录摘要（只含名称与哈希，不含 schema） |
| `exec.run` | 请求 | `execId`、`source`（内联代码或会话内路径）、`inputs`（JSON）、`timeoutMs`、可选 `entry` | 执行结束时应答：状态、返回值、异常类型与摘要后的 traceback、统计 |
| `exec.cancel` | 通知 | `execId` | SDK 在执行线程里抛 `KeyboardInterrupt`；超过 `cancelGraceMs` 宿主强杀 |
| `session.shutdown` | 通知 | 原因 | 优雅退出 |
| `ping` | 请求 | - | 心跳，可选 |

沙箱到宿主：

| 方法 | 类型 | 参数 | 说明 |
|---|---|---|---|
| `tools.list` | 请求 | `query`、`detail`（`name`/`brief`/`full`）、`limit` | 仅桥接开启时可用；渐进式披露；只返回 `needs.bridge` 声明范围内的工具 |
| `tools.call` | 请求 | `name`、`arguments`（JSON 对象） | 仅桥接开启时可用；返回 `{content: string, isError}`；经桥接与策略链（第 6 章） |
| `skills.list`、`skills.describe` | 请求 | 同上 | 仅桥接开启时可用；skill 元数据（名称、描述、兼容性说明）；正文与脚本通过只读挂载读取 |
| `artifact.publish` | 请求 | `path`（须在 `outbox` 内）、`kind`、`description` | 立即触发校验与登记；返回产物 ID、大小、sha256 |
| `emit` | 通知 | `level`（`log`/`progress`/`event`）、`data` | 执行期间向宿主推送事件，宿主可转成流式事件展示（例如长任务的进度） |
| `net.fetch` | 请求 | `method`、`url`、`headers`、`body`（小的内联，大的引用 `outbox` 内文件）、`timeoutMs` | 仅 `needs.network` 获批且 `network.mode=brokered` 时可用；宿主按 8.2 的规则执行，返回状态码、头与受限大小的响应体（超限时落到 `inbox` 并返回引用） |

### 5.4 错误码

在 JSON-RPC 保留码之外，应用错误占用 -32001 起：

| 码 | 含义 | 模型会看到的信息 |
|---|---|---|
| -32001 | `PolicyDenied`（不在白名单或被策略链拒绝） | 简短原因，不泄露其他工具名 |
| -32002 | `ApprovalRefused` | 用户拒绝及其理由 |
| -32003 | `ApprovalTimeout`（含 `Suspend` 折算） | 说明需要在 `needs.bridge` 预先声明 |
| -32004 | `BudgetExceeded`（调用次数、速率、并发） | 剩余额度 |
| -32005 | `ToolError`（工具自身失败） | 工具原始错误文本 |
| -32006 | `Cancelled` | - |
| -32007 | `PayloadTooLarge` | 上限值 |
| -32008 | `NotAvailable`（后端能力不足，如无代理网络） | 能力矩阵中的原因 |

### 5.5 版本协商

协议版本为语义化版本。SDK 与宿主同源分发，版本不一致几乎不会发生；一旦握手发现主版本不匹配，直接拒绝并给出明确提示。SDK 目录按协议版本分目录存放，升级后旧会话不受影响。

### 5.6 对 Agent（模型）暴露的接口

对模型只暴露一个工具 `run_python`，参数：

| 参数 | 必填 | 说明 |
|---|---|---|
| `code` | 二选一 | 要执行的 Python 源码 |
| `script` | 二选一 | 对话工作目录或只读挂载的 skill 里已有的脚本路径（不能指向宿主任意路径） |
| `reason` | 是 | 一句话说明“为什么现有工具做不了”。展示在审批提示里，写入审计。强制模型先想清楚是不是真的需要沙箱，也让人看得懂意图 |
| `inputs` | 否 | JSON 对象，受 `ipc.inlineMaxBytes` 限制；代码里用 `sandbox.inputs` 取 |
| `needs` | 否 | 能力申请，见 1.4.2：`network`、`read`、`exports`、`bridge`；后置的 `packages` 启用后加入 |
| `timeout_secs` | 否 | 默认 120，不超过 `limits.wallTimeSecs` 的上限 |

返回内容（文本，供模型读取）：

| 部分 | 内容 |
|---|---|
| 状态 | 成功，或失败类别（见 1.4.4）及下一步提示 |
| 返回值 | `set_result` 的 JSON；过大时自动落文件，只给摘要与路径 |
| 输出 | stdout 与 stderr，首尾保留、中间截断 |
| 产物 | `outbox` 文件清单（名称、大小、sha256、简短预览）；已按 `needs.exports` 写回的位置 |
| 用量 | 墙钟、CPU、峰值内存；若有桥接调用，附摘要，例如“共 37 次调用：read_file×35、grep×2” |

桥接调用不写进 LLM 的对话记录（它们属于父调用内部）。因此：审计日志是它们唯一的完整记录，结果里的桥接摘要是给模型和人看的简要线索。

后续阶段可能新增只读的 `python_env`（查看当前预置包与限制），用来弥补工具说明在注册时定格的限制（1.4.5）。

### 5.7 Python SDK 的接口面

只描述能力，不描述实现：

- `sandbox.inputs`：本次执行的输入。
- `sandbox.set_result(x)`：设置返回值，这是向模型交付“答案”的唯一途径；不会去猜“最后一个表达式”。不可序列化的对象由 SDK 给出摘要或报错（1.4.4）。
- `sandbox.emit(...)`、`sandbox.publish(path)`。
- 目录常量：`work_dir`、`inbox_dir`、`outbox_dir`；配置了共享目录时再有 `shared("名称")`。
- `tools`、`skills`：**仅桥接开启时存在**（`needs.bridge`），否则没有这两个对象。按需生成存根：`tools.read_file(file_path=...)`；`tools.search(query, detail)`；`tools.call(name, **args)`。工具名里含 `-` 的（如 `demo__get-sum`）无法成为 Python 标识符，存根会做规范化，规范化后冲突的只能用 `tools.call(name, ...)`。
- 说明：工具的返回类型目前都是字符串（`Tool::execute` 返回 `String`），SDK 原样给出，不做类型猜测。多模态结果要等多模态输入的执行项（gap-analysis 第 13 项）。

### 5.8 协议硬化

- 状态机：必须先握手；握手之前的任何其他消息都是违规。
- 每次执行的限制：最大并发请求数、总调用数、每分钟调用数、单次参数和返回大小、嵌套深度。
- 超时：握手超时、单请求超时、心跳超时。
- 帧大小在读取前检查；JSON 深度与键数量设上限。
- 读写使用独立任务，防止沙箱不读响应而拖死宿主（背压：响应队列有界，满了就断开）。
- 所有来自沙箱的字符串在进入日志和提示前都要转义。

## 6. 宿主能力桥接（工具与 skill）

### 6.1 原则

0. **桥接是次要路径，默认关闭**：缺口兜底的典型任务是“算一下、转一下、抓一下”，不需要在代码里编排宿主工具。桥接的价值在批处理与省 token（中间结果留在 Python 变量里），这是进阶用法。因此 `needs.bridge` 为空时，沙箱里没有 `tools`、`skills` 对象，通道上也不处理 `tools.*`、`skills.*`。落地顺序也靠后（P4）。
1. **没有第二套权限体系**：嵌套调用必须经过与 Agent 直接调用相同的策略链，否则“用代码调工具”就成了绕过 `WorkspaceGuardCallback` 与审批的后门。
2. **默认全拒绝，白名单放行**：`bridge.tools.allow` 是**可以被声明的上限**，不是默认开启的集合；某次调用能用到哪些，取决于它的 `needs.bridge` 与这个上限的交集。
3. **桥接是特权升级面**：能从沙箱里调用 `run_command`、`write_file`，等于沙箱形同虚设。这类工具默认不可桥接。
4. **结果留在沙箱里**：工具返回值进入 Python 变量，不自动进入模型上下文；只有 stdout、返回值、产物清单会回到模型。这既省 token，也减少敏感数据流向模型（参考 Anthropic 文章）。

### 6.2 工具暴露：代码即 API

- 宿主根据 `ToolRegistry` 里每个工具的 `ToolDefinition`（名称、描述、JSON Schema）为 Python 生成存根；存根按需生成，不在启动时全量下发，沙箱先看到的只是名称与摘要。
- 渐进式披露：`tools.search(query, detail)` 分三档详细程度，与 Anthropic 文章的建议一致。
- 存根不是安全机制。宿主对每个 `tools.call` 都重新校验：名称是否在白名单、参数是否为 JSON 对象、大小是否超限，参数内容由工具本身和策略链校验。
- 并发：沙箱可能从多个线程发起调用。宿主按 `Tool::concurrency_safe()` 的语义调度：非并发安全的工具串行执行（沿用 `src/tools/schedule.rs` 的规则）。

### 6.3 策略链、审批与上下文

- 嵌套调用的上下文来源见 3.3 的选项 A（task-local 句柄）与选项 B（扩展 `Tool`）。
- 审批：沿用 `DualApprovalCallback` 的通道，但把 `WhenUnanswered` 强制为 `Refuse`。`Suspend` 折算成拒绝（4.3）。
- 取消：`ExecutionContext.cancellation` 触发时，桥接中的调用一并取消，并让沙箱收到 `Cancelled`。
- 备选的挂起方式：见 4.3 第 7 条（中止并重放）。首版仍是“`Suspend` 视为拒绝”。
- 记账：桥接调用产生的模型用量（例如 `read_image`、子 agent）要计入父运行，所以必须在同一任务内执行。

### 6.4 桥接策略

下表的“默认”指**能否出现在 `bridge.tools.allow` 上限里、被 `needs.bridge` 声明**，不是“默认就能用”。

| 类别 | 例子 | 默认 | 说明 |
|---|---|---|---|
| 纯计算 | `calculator` | 允许 | 无副作用 |
| 本地只读 | `list_files`、`read_file`、`grep` | 允许；可被 `manifest` 预批 | 仍经路径守卫，与 Agent 直接调用完全一致：读取时现有守卫只拒 `.env*`，`.git/`、`.agent/`、`mcp.json` 目前是可读的。桥接不比直接调用更松也不更紧；要收紧读取范围，应改守卫本身（7.5），不是给桥接另立一套 |
| 出站 | `web_search`、远程 MCP 工具、`read_image`（调用视觉模型） | **拒绝** | 这些工具是外泄通道：即使沙箱网络关闭，经桥接的查询字符串也能把数据带出去 |
| 写入或破坏 | `write_file`、`edit_file`、`delete_file`、`unzip_file` | 拒绝；可按名字加入白名单，只能逐次审批（`each`），**不可被 `manifest` 预批**（4.3 第 6 条） | 推荐改用“产物暂存再写回”（7.2） |
| 执行 | `run_command` | **硬拒绝**，仅在 `bridge.allowRunCommand` 显式打开时可用，且每次审批 | 执行类桥接等于逃出沙箱 |
| 自身递归 | `run_python` | **硬拒绝** | 防止嵌套沙箱和资源放大 |
| 子 agent | `AgentTool` | 拒绝 | 代码循环调用模型会放大成本，需要额外预算 |
| 记忆 | `remember`、`forget` | 拒绝 | 沙箱不应能写长期记忆 |

目前 `Tool` 只有 `concurrency_safe()` 一个粗粒度元数据，分类靠配置里的名字白名单。后续可以考虑给 `Tool` 增加能力分类字段，把上表中的类别变成工具自述，减少按名字配置的负担。

### 6.5 Skill 模型

仓库里没有 skill，这里定义一个最小集，遵循 Agent Skills 规范：

- **发现与校验**：按 `skills.roots` 扫描目录，校验 frontmatter（`name` 与目录名一致且符合字符规则、`description` 长度、`compatibility` 长度）。校验失败的 skill 跳过并记录，不影响其他 skill。
- **三种暴露形式**：
  1. 指令型：`SKILL.md` 由模型通过读文件或加载工具读取。不涉及沙箱。
  2. 沙箱内脚本：skill 目录只读挂载到沙箱；脚本用 `run_python(script=...)` 执行。第三方脚本与 Agent 生成的代码同等不可信，不因为“是 skill”而提升权限。
  3. 宿主中介型：需要宿主凭据或网络的能力，实现成宿主侧的 `Tool`（随 skill 配置注册），沙箱经 `tools.call` 调用，与任何其他工具一样走策略链。**不引入第二种执行路径**。
- **`allowed-tools`（规范里的实验字段）**：当 `run_python` 的 `script` 来自某个 skill 时，有效的桥接白名单取“配置白名单”与“该 skill 的 `allowed-tools`”的交集。这是可选加固。
- **依赖**：`compatibility` 只是说明，不用来自动安装。skill 脚本需要的库必须在预置档里；缺依赖时和 Agent 的代码一样会报缺依赖错误。启用后置的按需安装后，可走 `needs.packages` 申请（9.6），始终不在沙箱里 `pip install`。
- **与缺口兜底的关系**：skill 是“已经有人整理好的办法”，应该排在现写代码之前（1.4 的决策顺序）；反过来，现写代码里反复有效的脚本，可以由人确认后沉淀成 skill（后续阶段，不在首版）。

### 6.6 数据流与泄露

| 路径 | 控制 |
|---|---|
| 工具结果 → Python 变量 | 留在沙箱，不进模型 |
| Python → stdout、返回值 | 进入模型上下文；`Capped` 截断；经 `AfterToolCallback` 可脱敏 |
| Python → `outbox` → 宿主 | 经回收校验；内容不自动读入模型 |
| Python → 桥接的出站工具 | 默认拒绝；放开时有限速与预算 |
| Python → 网络 | 默认关闭（8.2） |
| 间接提示注入 | 工具结果和产物内容可能带攻击者文本，进入模型前要有“来自不可信来源”的标注，与记忆召回的做法一致 |

## 7. 文件系统与数据传递

### 7.1 目录布局

```
<数据目录>/sandbox/
  runtime/<py-version>/            只读   受管 Python
  envs/<profile>-<lockhash>/       只读   预置依赖（离线构建，哈希锁定）
  sdk/<protocol-version>/          只读   sandbox_sdk 与工具存根
  envs/overlays/<lockhash>/        只读   （后置，P5）按需安装的依赖层（9.6），由 DependencyBroker 构建，可跨调用复用
  conversations/<conversation-key>/ 按对话保留（4.5）；目录名是对话键的哈希，不含原始 id
      work/                        读写   工作目录（cwd），同一对话的多次调用共用
  runs/<run-id>/                   每次调用新建，结束即删
      tmp/                         读写   TMPDIR
      inbox/                       只读   宿主 -> 沙箱（needs.read 的复制件）
      outbox/                      读写   沙箱 -> 宿主
<数据目录>/sandbox/.state/         宿主私有   元数据（沙箱不可见）
```

- `skills.roots` 下的 skill 目录按只读挂载。
- 数据目录默认放在 `--workspace` 的 `.agent/sandbox/` 下（`.agent/` 在现有守卫里写入受保护）；沙箱只被授予其中本次调用的 `work`、`tmp`、`inbox`、`outbox`，`.agent/` 其余部分（会话、审批、记忆库）不可见。
- **这个默认值有两个代价，需要明说**：(1) 仓库的 `.gitignore` 目前只忽略 `.env`、`mcp.json`、`tenants.json`，没有 `.agent/`，沙箱目录会出现在 `git status` 里，落地时要补上忽略规则；(2) 这是“沙箱可写、宿主工具可读可执行”的区域，而且在工作区之内：`run_command` 的守卫只检查 `workdir`（`guarded_fields`），基线自动执行时写进 `work` 的脚本，之后可以被一次经批准的 `python .agent/sandbox/.../x.py` 运行，审批人看到的只是一行命令，看不到脚本内容。这条路径要写进 R10。备选是把数据目录放到用户数据目录（例如 `~/.agent/sandbox/<工作区哈希>/`），工作区里不留可执行内容；代价是跨工作区的磁盘占用更难管理。取舍见 15.2 第 13 项，首版倾向后者。
- 其他对话的 `work`、其他调用的 `runs/*` 对本次沙箱不可见。

### 7.2 三种传递通道

兜底场景里，用户的文件由 Agent 在调用里按需申请，不预先挂载任何东西（1.4.2）。

| 通道 | 方向 | 适用 | 机制 | 限制 |
|---|---|---|---|---|
| 内联 | 双向 | 小的 JSON 或文本 | `inputs`、`set_result` 的返回值、RPC 参数 | `ipc.inlineMaxBytes`（默认 256 KiB）；二进制用 base64 |
| 申请式复制 | 宿主到沙箱：`needs.read` → `inbox`；沙箱到宿主：`outbox` → `needs.exports` | 用户文件（表格、PDF、图片）与处理结果 | 宿主按申请**复制**文件进 `inbox`（不用硬链接，避免与原文件共享 inode）；`outbox` 的产物经回收校验后，按 `needs.exports` 复制到工作区 | 文件数、总大小、单文件大小上限；入站按 7.4“入站”逐项校验，路径过守卫加读拒绝清单；导出过守卫加写拒绝清单（7.5），视为一次写入，需批准 |
| 共享挂载（可选） | 取决于模式 | 运维预先配置的目录，沙箱需要反复直接读写（如大数据目录） | 按 `shared` 配置授权 | 见 7.3 |

**写回工作区的唯一路径**：沙箱不直接写工作区。结果先落在 `outbox`，宿主校验（7.4）后按 `needs.exports` 复制；目标路径过路径守卫，再过写回拒绝清单（7.5；守卫自带的写规则是 `.env*`、`.git/`、`.agent/`、`mcp.json`，清单比它更宽），且视为一次写入，需要批准。**落地写入本身也要防替换**：校验通过后到真正写入之间，目标路径上的某一级可能被换成符号链接（沙箱本身写不到工作区，但工作区里的其他进程可以）。所以宿主要从工作区根开始逐级打开、不跟随符号链接，再创建目标文件；不能先校验字符串、再用会跟随链接的 `std::fs::copy` 之类的调用写入。已存在的目标文件被覆盖时，审批提示里标明。直接把项目目录以读写方式挂进沙箱是高风险选项，默认不提供。

### 7.3 共享目录模式（运维可选）

这一节是运维在配置里预先声明的**长期共享目录**，不是兜底的主路径：Agent 临时要处理某个文件，用 `needs.read`；只有目录大、需要反复读写时，才值得配成共享挂载。

| 模式 | 沙箱权限 | 宿主处理 | 风险 |
|---|---|---|---|
| `ro` | 只读 | 无 | 低；但会暴露目录里的所有内容，包括 `.env*`，所以必须配合 `deny` 通配符（7.5） |
| `rw` | 读写，直接落在宿主目录 | 无校验 | **高**：沙箱可植入符号链接、`.git/hooks`、`sitecustomize.py`、`.pth`、`.vscode/tasks.json`、CI 配置等，之后被宿主用户的工具执行。默认禁用，开启时在配置里需要显式 `allowDirectWrite` |
| `stage`（推荐） | 读写的是会话内的副本 | 结束时对副本做差异比对，经回收校验后由宿主工具写回，需要审批 | 中；成本是复制 |
| `inbox` / `outbox` | 见 7.2 | 同上 | 低 |

### 7.4 复制校验：出站回收与入站复制

两个方向各有一套规则，规则相近但不能互相代替。**出站**（沙箱到宿主）的校验对象是沙箱产出的、完全不可信的文件；**入站**（宿主到沙箱）的校验对象是用户工作区里的文件，攻击面是“宿主被沙箱代码诱导去读不该读的东西”。

**出站（`outbox` 回收，适用于所有宿主读取沙箱产出的地方）**：宿主逐项执行，任何一项失败，该文件被拒绝并记入审计：

1. 用 `lstat` 判断类型，只接受普通文件；符号链接、设备文件、命名管道、套接字一律拒绝。
2. 从 `outbox` 根开始逐级打开并禁止跟随符号链接（Linux 可用 `openat2` 的 `RESOLVE_BENEATH`，其他平台用逐级 `O_NOFOLLOW` 等价方案），防止校验后被替换（TOCTOU）。
3. 文件名规范化：拒绝 `..`、绝对路径、NUL；Windows 上还要拒绝保留名（`CON`、`NUL` 等）、末尾点或空格、备用数据流（`:stream`）。
4. 文件数、总大小、单文件大小、目录深度设上限。
5. 计算 sha256 并登记；不保留可执行位。
6. 不自动执行、不自动解压、不自动读入模型上下文。

“适用于所有宿主读取沙箱产出的地方”包括 P0 的**结果文件**：沙箱里的代码可以把结果文件建成指向 `~/.ssh/id_rsa` 之类的符号链接，宿主若跟随读取再回给模型，就成了被借权的代理人。所以第 1、2、4 条在 P0 就必须生效，不能等到 P1 的回收校验（15.1）。

**入站（`needs.read` → `inbox`）**：

1. 守卫和读拒绝清单（7.5）对**每一个条目**都判一遍，不只判申请的那个路径。守卫只检查传入路径自身的各级组件，申请 `data/` 时，目录里嵌着的 `data/.env`、`data/.git/` 它看不到，递归复制必须自己逐项过清单。
2. 逐项 `lstat`；只接受普通文件和目录。符号链接一律拒绝（既不跟随，也不把链接本身复制过去）；设备文件、命名管道、套接字拒绝，其中命名管道尤其要在 `open` 之前拒掉，否则宿主会阻塞在读上。
3. 申请路径本身经规范化后必须仍在工作区内（符号链接指到工作区外的，规范化后会落到外面，拒绝）；打开时逐级不跟随符号链接，防止校验后被替换（TOCTOU）。
4. 文件数、总大小、单文件大小、目录深度设上限，超限整体拒绝，不做部分复制后静默截断。
5. 复制而不是硬链接；`inbox` 里的文件不保留可执行位；文件名规范化同出站第 3 条。
6. 复制完成后对副本计算 sha256 并写入审计，便于事后核对沙箱读到的是什么。

### 7.5 受保护路径

先看现有守卫的实际行为（代码事实，`path_guard.rs` 的 `protected(relative, write)`），因为它**按读写方向区分**：

| 路径 | 读取时 | 写入时 |
|---|---|---|
| `.env*` | 拒绝 | 拒绝 |
| `.git/` | 允许 | 拒绝 |
| `.agent/` | 允许 | 拒绝 |
| `mcp.json` | 允许 | 拒绝 |

守卫的文档里明说读 `.git/config` 是普通操作，所以不应为了本方案去改守卫、让直接调用的 `read_file` 也读不了这些。但 `needs.read` 的风险不同：文件被复制进沙箱，再叠加 `needs.network` 就能外泄（R18），而 `mcp.json` 里有 `env` 和 `Authorization` 令牌（`mcp.example.json` 可见）。因此本方案**不复用**守卫的集合，按用途定义三份清单，默认值由项目维护，均可配置（只在用户级配置里放宽，10.2）：

1. **读拒绝清单（`needs.read` 用，`escalation.readDeny`）**：守卫的读规则（`.env*`），加上 `.git/`、`.agent/`、`mcp.json`，以及 `.ssh`、`.aws`、`.npmrc`、`.netrc`、`.pypirc` 这类常见凭据文件名（工作区里偶尔会有，具体名单落地时再补全）。目录递归复制时对每个条目都判（7.4 入站第 1 条）。
2. **写回拒绝清单（`needs.exports[].to` 用，`escalation.exportDeny`）**：守卫的写规则（`.env*`、`.git/`、`.agent/`、`mcp.json`），加上 `.vscode/`、`.idea/`、`.github/workflows/`、`*.pth`、`sitecustomize.py`、`usercustomize.py`、shell 的 rc 文件。`exports` 是沙箱产物落进工作区最常用的路径，R10 的持久化投毒主要从这里进来，所以这份扩展清单不能只给共享挂载用。
3. **共享挂载拒绝清单（`shared[].deny`）**：默认值取上面两份的并集（`ro` 模式至少含读拒绝清单，`rw`、`stage` 含写回拒绝清单）。

守卫本身的回归测试（`every_builtin_tool_is_classified_for_the_guard`）只管“工具是否登记”，不管清单内容；上面三份清单各自要有测试（14 章）。

## 8. 权限模型与资源限制

### 8.1 能力等级

沿用此前设计的 `off / read / write / net` 四档。采用能力申请模型后，它们的含义是**运维设定的上限**：每次调用都从同一个基线出发，Agent 通过 `needs` 申请，最多只能被授予到这个上限。

| 等级 | 上限：`needs` 最多能被授予什么 | 说明 |
|---|---|---|
| `off` | 无 OS 隔离，仅有超时、进程组回收和输出截断（等同今天的 `run_command`） | 必须显式指定；横幅标红提示；审计记录；任何调用都要询问（1.4.3） |
| `read` | 预置依赖；`needs.read`（复制进沙箱） | 不允许导出、联网、桥接（装新包在首版不存在）。适合只做分析 |
| `write`（**默认**） | `read` 的全部，加 `needs.exports`、`needs.bridge`；后置的 `needs.packages` 启用后也在这一档 | 不允许联网 |
| `net` | `write` 的全部，加 `needs.network` | 联网方式见 8.2 |

**基线**（每次调用都有，不需要申请）：只读的运行时、SDK、预置依赖、skill；本对话的 `work`、本次的 `tmp`、`outbox`；关闭的网络；极小的环境变量白名单；没有桥接。

询问规则（对应 1.4.3）：

| 申请项 | 上限不够时 | 上限够时 |
|---|---|---|
| 预置依赖、无 `needs` | - | 自动执行（`approval.baseline=auto`，前提是隔离已确认生效） |
| `needs.read` | 直接拒绝，提示“本部署不允许” | 询问（显示文件清单与大小） |
| `needs.packages`（后置，P5） | 同上 | 询问（显示包名、版本与来源，9.6） |
| `needs.exports` | 同上 | 询问（显示目标路径；已存在的文件显示将被覆盖） |
| `needs.network` | 同上 | 询问（显示域名清单，过宽的通配符直接拒绝） |
| `needs.bridge` | 同上 | 询问（显示工具清单） |
| 暂时没人回答（前端在，但在超时内没人答） | - | 外层 `run_python` 调用沿用现有 `WhenUnanswered`（默认 `Suspend`）：沙箱还没启动，可以挂起，等人回来再恢复（1.4.3） |
| 没有前端（批处理、定时任务，`escalation.unattended=refuse`） | 一律拒绝所有升级项，按基线执行或报错，**不挂起** | 同左 |
| 审批未接线（库使用者只注册了工具，没配审批规则，也没选择免审批） | 升级项一律不可用，只做基线，返回“本部署未接入审批，升级项不可用”（1.4.3 末条） | 同左 |

**配置里的上限（`sandbox.level`）不等于工具这一刻持有的上限**：工具持有的上限 = 配置上限与“审批是否接线或明确免审批”的交集，后者不成立时只有基线。

默认等级叫 `write`，但没有被批准的 `needs.read` 时，宿主文件系统对它实际是不可见的。这与“默认对宿主受限”并不冲突。默认**不开放联网**，这会让“抓取网页”这类常见缺口任务在默认配置下被拒（返回“本部署未开放联网，请告知用户”），这一点已定：默认上限保持 `write`，不开放联网（15.2 第 2 项）；需要联网的用户通过 `--isolation net` 显式打开。

### 8.2 网络

| 模式 | 含义 | 实现思路 | 平台限制 |
|---|---|---|---|
| `off`（默认） | 无任何网络 | Linux：网络命名空间；macOS：Seatbelt 禁网；Windows：AppContainer 不授予网络能力 | 三平台都可 |
| `brokered` | 沙箱里仍然没有网络；代码通过 SDK 的 `sandbox.http` 发请求，由宿主代为执行并返回 | 经通道上的 `net.fetch`（5.3）；宿主做域名白名单、解析地址检查、响应大小与超时限制 | **三平台都可用**，不需要 OS 网络配置。局限：直接用 `requests`、`urllib`、`pandas.read_csv(url)` 的代码不能原样运行，要改用 `sandbox.http`；只支持 HTTP(S)，不支持任意 TCP；是否对常用库做垫片兼容是【待验证】 |
| `proxy` | 沙箱里有网络路径，但只能连宿主侧过滤代理，代理按域名白名单出站 | 参考 `sandbox-runtime`：宿主运行代理，沙箱只能连代理。Linux 经 Unix socket 桥接，macOS 只允许连回环上的代理端口。现成库不用改 | Windows 需要回环豁免或 WFP 过滤器，都要管理员权限，第一版不支持；Landlock-only 兜底下 UDP 不受控，不支持（见 9.5） |
| `full` | 不限 | - | 等价于放弃网络隔离，必须显式配置，并提示外泄风险 |

**选择**：`needs.network` 被批准时，按 `network.mode` 配置决定用 `brokered` 还是 `proxy`。推荐首版先做 `brokered`：缺口任务最常见的联网需求是“抓一个页面、调一个接口”，`brokered` 覆盖它，且三个平台行为一致，免去 Windows 上的网络授权难题。`proxy` 作为第二步，用于必须使用现成库的场景。

**过滤规则**（`brokered` 与 `proxy` 共用，参考 `sandbox-runtime`，**【已核实】**其做法）：拨号前先解析域名，丢弃回环、链路本地、多播、云元数据地址和本机网卡地址，再连接已通过检查的那个地址（不二次解析），防止 DNS 重绑定。拒绝列表优先于允许列表。重定向要逐跳重新检查。

**批准的域名只是这一次调用的白名单**，不写入配置；代理或宿主在调用结束时关闭对应的放行。

**凭据不进沙箱**（备选，不进首版）：Claude Code 的做法是 git 凭据不进沙箱，沙箱内只有范围受限的自定义凭据，由代理验证操作后附上真实令牌；Cloudflare 同样不让凭据和客户端对象进沙箱（2.4 第 6 条）。本方案的沙箱本来就拿不到宿主环境变量（8.4）。以后出现“需要认证的接口”这类任务时，应该由宿主在 `net.fetch` 里按域名附加凭据，而不是把令牌传进沙箱；对应的配置（域名到凭据的映射）要放在用户级配置里，且不能出现在审批提示或审计日志的明文里。

沙箱里**不运行 `pip install`**。依赖由宿主侧准备（9.6），所以“联网”和“装包”是两个独立的申请，批准装包不会顺带开放联网。

### 8.3 资源限制矩阵

| 资源 | Linux | macOS | Windows | 备注 |
|---|---|---|---|---|
| 墙钟 | 宿主定时器杀进程树 | 同 | 同 | 与 `run_command` 一致，默认 120 秒，上限 600 秒 |
| CPU 时间 | `RLIMIT_CPU` | `RLIMIT_CPU` | Job 的用户态时间上限 | 墙钟之外的第二道 |
| 内存 | cgroup v2（若可委派），否则 `RLIMIT_AS`（限制虚拟内存，部分库会不兼容） | `RLIMIT_AS` 的约束力不可靠（**【待验证】**），改用宿主看门狗轮询 RSS 并终止 | Job 内存上限（可靠） | macOS 上最弱。**`data` 档与 `RLIMIT_AS` 的冲突**（背景知识，**【待验证】**，P0b 实测）：numpy、OpenBLAS、pandas 导入时会预留大量虚拟地址，常常在 1 GB 的 `RLIMIT_AS` 下就导入失败。所以 `RLIMIT_AS` 回退只用于 `base` 档；`data` 档在 cgroup 不可用时，改用与 macOS 相同的 RSS 看门狗，不用 `RLIMIT_AS` |
| 进程与线程数 | PID 命名空间加 cgroup `pids.max` | 无可靠的每沙箱计数（`RLIMIT_NPROC` 是整个用户维度，不适合）；看门狗按进程树计数 | Job 的活动进程上限 | Linux 上 `pids.max` 按线程（task）计数，不只是进程（背景知识，**【待验证】**）。numpy 与 OpenBLAS 默认按核数起线程，`maxProcesses=64` 在多核机器上可能一导入就用光，所以要同时在环境变量里限制线程数（8.4），并把默认值放到实测后再定 |
| 打开文件数 | `RLIMIT_NOFILE` | 同 | 句柄由 Job/系统限制 | |
| 单文件大小 | `RLIMIT_FSIZE` | 同 | 无直接对应，靠看门狗 | |
| 磁盘配额 | 对 `work`/`tmp`/`outbox` 用容量受限的 tmpfs（bwrap 路径）；否则看门狗 | 看门狗轮询目录大小并终止 | 看门狗 | 没有可移植的磁盘配额 |
| core dump | `RLIMIT_CORE=0`、禁止被调试 | 同 | 关闭错误报告 | |
| 输出 | `Capped` | 同 | 同 | 复用现有实现 |
| RPC | 帧大小、速率、并发、总调用数 | 同 | 同 | 5.8 |

### 8.4 环境变量与 Python 加固

- 子进程使用 `env_clear` 加白名单（仅 `PATH` 的受控值、`LANG`、会话路径常量、SDK 需要的变量）。比 `run_command` 的 `strip_secrets` 黑名单更严；`.env` 里的密钥不会因为名字不像凭据而漏进来。
- **`data` 档需要的几个变量**（现有 stdio MCP 的白名单是 `PATH`、`HOME`、`TMPDIR`、`LANG`、`LC_ALL`，其中 `HOME` 不能原样带给沙箱，所以要显式列出）：`HOME`、`XDG_CACHE_HOME`、`XDG_CONFIG_HOME`、`MPLCONFIGDIR` 都指向本次的 `tmp`（matplotlib、pandas 等会往这些位置写缓存与配置，指向宿主真实目录既会失败也会泄露路径）；`OMP_NUM_THREADS`、`OPENBLAS_NUM_THREADS`、`MKL_NUM_THREADS` 设成较小的固定值（与 8.3 的线程数上限配合；具体值 P0b 实测后定）；`MPLBACKEND=Agg`（无界面绘图，9.6）。这些值由宿主写死，不接受调用方传入。
- Python 以隔离模式启动（忽略 `PYTHON*` 环境变量、用户站点包，且当前目录不进入 `sys.path`），不写字节码，不加载用户站点目录。这些只是降低意外泄露，**不是安全边界**。
- 不在沙箱里提供 `PYTHONSTARTUP`、`sitecustomize` 的宿主版本。

## 9. 跨平台适配

### 9.1 后端矩阵

| 平台 | 首选后端 | 兜底后端 | 都不可用时 |
|---|---|---|---|
| macOS | Seatbelt（由 helper 调用，或经 `sandbox-exec`） | 无 | 拒绝运行 |
| Linux | bubblewrap（用户/PID/网络/IPC/UTS 命名空间，只读绑定，tmpfs，丢弃能力）加 seccomp 加 Landlock | Landlock 加 seccomp（无命名空间） | 拒绝运行 |
| Windows | AppContainer 加 Job Object（无需管理员） | 受限令牌加低完整性级别加 Job（无网络隔离，仅用于 `net=full`） | 拒绝运行；可选“专用本地用户加 WFP”（需一次性管理员安装） |
| 通用 | 容器后端（可选，面向服务端） | - | - |

“拒绝运行”是默认行为。`sandbox.fallback = degrade` 才允许落到兜底后端，并且**任何情况下都不会自动降到 `off`**。

### 9.2 macOS

- 使用 Seatbelt。`sandbox-exec` 命令行官方标记为弃用，但 `sandbox-runtime` 与 Codex 均在使用；它的 profile 语言属于私有接口，随系统升级可能变化。因此后端需要对不同系统版本做自检，并把 profile 生成集中在一处。
- profile 以“默认拒绝”起步：允许读运行时、SDK、系统库（`/usr/lib`、`/System/Library`、dyld 缓存等必要部分）、本次授权的工作与运行目录；限制 `mach-lookup` 只放行必要服务；禁止网络；禁止 `process-exec` 之外的可执行文件。
- 必须阻止 Apple Events（`sandbox-runtime` 文档指出开启 `allowAppleEvents` 后沙箱不再提供代码执行隔离，**【已核实】**）。
- Seatbelt 支持在“已允许”的目录里再挖出拒绝项，所以共享挂载里的受保护路径可以直接表达。

### 9.3 Linux

- 优先 bubblewrap：用户命名空间、PID 命名空间、网络命名空间；退出时随父进程终止；新会话防止终端注入；根文件系统以只读绑定逐项构造，不暴露宿主 `/home`、`/root`。
- seccomp：拒绝 `ptrace`、`mount`、`unshare`、`setns`、`bpf`、`perf_event_open`、`keyctl`、`userfaultfd` 等；新的命名空间创建要拒绝，防止沙箱内自己创建用户命名空间把只读绑定解开（`sandbox-runtime` 同样加了这层，**【已核实】**）。`io_uring` 的攻击面较大，默认拒绝（**【待验证】**对 Python 常见库的影响）。
- 用户命名空间可能不可用：Ubuntu 24.04 起默认被 AppArmor 限制（Codex 与 `sandbox-runtime` 的文档都提到，**【已核实】**）；容器内常常也没有。此时走 Landlock 兜底，并在横幅里显示降级后的隔离类型。
- root 用户运行时 bubblewrap 可能因缺少能力而失败（`sandbox-runtime` 文档提到需要 `CAP_SETFCAP`，**【已核实】**），推荐以非 root 用户运行。
- Landlock：非特权可用；通过 `landlock` crate 的 best-effort 模式，**必须检查返回的状态是否为完全生效**，部分生效按失败处理；多线程默认只限制当前线程，所以必须在单线程的 helper 里、`exec` 之前应用。

### 9.4 Windows

- **AppContainer（首选，无需管理员）**：进程默认没有文件、注册表、网络访问，只能访问被授予的位置。Python 运行时目录需要给 AppContainer 授权，所以运行时必须放在**我们管理的目录**里，授权只做一次，不去改用户目录的 ACL。
- **Job Object**：设置内存上限、活动进程数上限、CPU 时间上限、关闭时终止（kill-on-close）、UI 限制。这是 Windows 上最可靠的资源与回收手段。
- **进程创建**：设置安全能力、句柄继承列表需要原生进程创建接口，`tokio::process::Command` 不够用，需要在 `windows-sys` 上自己封装，并把管道包装成异步流。
- **网络**：AppContainer 默认没有网络能力，回环也默认被阻断，所以 `off` 天然成立，`proxy` 在第一版不支持。联网需求由 `brokered` 模式满足（8.2）：沙箱里仍然没有网络，请求经通道交给宿主执行，所以 Windows 上“抓取页面、调接口”这类缺口任务第一版也能做，只是代码要使用 `sandbox.http`。
- **用户文件**：兜底的主路径（`needs.read` 复制进 `inbox`、`needs.exports` 复制出去）只需要给 AppContainer 授权我们自己管理的运行目录，**不改用户目录的 ACL**，这是这一路径在 Windows 上的一个好处。
- **共享目录**（运维预挂，可选）：需要给 AppContainer 授予目标目录的 ACL。`sandbox-runtime` 的 Windows 实现把这类授权**长期保留**，**【已核实】**这是它的一个已知缺点；本方案要求：授权必须记录、会话结束时撤销、崩溃后下次启动清理残留。
- **可选的增强档**：专用本地用户、WFP 出站过滤、受限写令牌，与 `sandbox-runtime`、Codex 的 elevated 模式同类，要求一次性管理员授权，用于需要 `proxy` 网络的场景。`sandbox-runtime` 报告受限令牌下系统 TLS（Schannel）会失败，因此 Windows 自带的 `curl`、PowerShell 网络命令、winget 等不可用，自带 TLS 栈的 Python 可以用（**【已核实】**其文档）；本方案的 AppContainer 路径不一定有同样问题，**【待验证】**。
- **WSL2**：在 WSL2 里运行 Linux 后端是另一种路线，本方案不作为首选，因为文件路径与性能语义不同。
- **【待验证】**：AppContainer 下继承的命名管道句柄可用；`python.exe` 与依赖的 DLL 在授权目录下可加载；`TEMP` 重定向后常见库工作正常。

### 9.5 能力对照与降级

| 能力 | macOS Seatbelt | Linux bwrap+Landlock+seccomp | Linux 仅 Landlock+seccomp | Windows AppContainer+Job |
|---|---|---|---|---|
| 白名单读取 | 支持（需维护系统库清单） | 支持（根文件系统只读绑定） | 支持，但系统目录通常要整体放行 | 默认即白名单 |
| 在已授权子树里挖拒绝项 | 支持 | 支持（只读绑定覆盖） | **不支持**（Landlock 只有允许规则） | 支持（拒绝 ACE，需 ACL 改动） |
| 网络 `off` | 支持 | 支持（命名空间） | 依赖 seccomp 拒绝 `AF_INET`/`AF_INET6` 的 `socket`，加 Landlock 网络规则（仅 TCP，**【待验证】**） | 支持 |
| 网络 `proxy` | 支持（只放行回环代理端口） | 支持（Unix socket 桥接） | **不支持**：放开 TCP 的同时 UDP 无法按端口限制，存在 DNS 外泄口 | 第一版不支持 |
| PID 隔离与整树回收 | 进程组加扫描，有残余风险 | 支持 | 无 PID 命名空间，进程组加扫描 | Job 可靠回收 |
| 内存上限 | 看门狗 | cgroup 或 `RLIMIT_AS` | 同 | Job 可靠 |
| 违规可观测 | 系统沙箱日志 | EACCES/EPERM；Landlock 审计特性依 ABI | 同 | 访问被拒的错误码 |

对共享目录的含义：Linux 仅 Landlock 兜底时，不能表达“可写工作区但保护 `.git`”，只能把可写授权下放到每个非受保护的子项，或者**直接拒绝 `rw` 共享**，只允许 `stage` 与 `ro`。

### 9.6 Python 运行时与依赖供给

缺口任务会 `import` 第三方库，依赖是否够用，直接决定兜底工具能解决多少任务。社区里最接近的参照（Anthropic 的托管 code execution tool）的做法是：**沙箱不联网、不装包，靠预装库覆盖常见任务**（2.4 第 1 条）。本方案首版采用同样的做法，分两层；第三层是后置能力。

1. **受管运行时**：默认使用受管的独立 Python 发行版（预编译、自带标准库，背景知识：如 python-build-standalone 一类，未联网核实）。固定版本，按平台与架构分发，校验哈希。
2. **预置依赖档（首版的核心）**：按“环境配置名”分档，由宿主离线构建，使用带哈希的锁定文件，只读挂载。`base` 只有标准库；`data` 是做厚的常用库集合（见下）。预置包名单写进 `run_python` 的工具说明（1.4.5）。
3. **按需安装（`needs.packages`，后置，P5）**：预置档之外的包，由 `DependencyBroker` 在**宿主侧**准备，沙箱里不联网、不运行 `pip`。何时做，见下面的“触发条件”。

#### 预置依赖档 `data` 的参考清单

下表的起点来自 Anthropic 文档公开列出的预装库，**只作为首版 `data` 档的候选**，不是已经验证过的清单：每个包是否有适用于三个平台、各 CPU 架构的预编译包，体积多大，许可证是否合规，都要在落地时逐个确认。

| 类别 | 候选库（Anthropic 文档中列出的） | 说明 |
|---|---|---|
| 数据处理 | pandas、numpy、scipy、scikit-learn、statsmodels | 体积最大的一块；scikit-learn 与 scipy 在部分平台上的预编译包要核实 |
| 可视化 | matplotlib、seaborn | 无显示环境时要用无界面后端 |
| 表格与办公文档 | openpyxl、xlsxwriter、xlrd、python-docx、python-pptx | 缺口任务里最常见的一类（格式转换、清洗） |
| PDF 与图片 | pypdf、pdfplumber、pypdfium2、pillow、reportlab | 其余的 pdf2image、pdfkit、tabula-py、Img2pdf 据背景知识依赖外部程序或 Java（**【待验证】**），**首版不建议带**，要带需确认运行时依赖也在沙箱里可用 |
| 数学 | sympy、mpmath | |
| 工具类 | tqdm、python-dateutil、pytz、joblib | |
| 命令行工具（Anthropic 容器里有） | unzip、7zip、bc、ripgrep、fd、sqlite | 这些是容器里的系统程序，不是 Python 包；本方案的沙箱里没有这些程序，是否需要，由审计数据决定（Python 标准库的 `zipfile`、`sqlite3` 已能覆盖其中两项） |

要补充的几点：

- **宿主工具已覆盖的不重复带**：例如文本搜索，宿主已有 `grep` 工具。
- **体积与启动**：预置档是只读挂载，不随每次调用复制，启动开销主要是解释器导入时间；大库（pandas、scipy）的首次导入要实测。
- **多档**：可以分 `base`、`data`、`docs`（办公文档与 PDF）几档，按需选 `python.envProfile`，避免每次调用都暴露全部库。是否要分档，取决于体积和导入耗时的实测结果。
- **更新**：预置档按固定版本发布，随发行包更新；安全漏洞修复靠换版本，不靠运行时升级。

#### 后置：按需安装

**触发条件**：不预设时间，用审计数据决定（13 章）。当满足下面任一条，再启动这一项：

- “缺依赖”类失败（`ModuleNotFoundError`）在 `run_python` 失败里占比持续偏高，且缺失的库集中在少数几个；这种情况优先**把这些库加进预置档**，不需要按需安装。
- 缺失的库分散、长尾，加进预置档不划算；这时才需要按需安装。

社区没有公开数据说明补位式代码工具里缺依赖的占比（2.4 末尾），这是我们要自己测的。

按需安装的流程：

1. Agent 在 `needs.packages` 里声明包名和版本约束（例如 `["openpyxl>=3.1"]`）。
2. `NeedsResolver` 按 `deps.allow`/`deps.deny` 过滤；拒绝名单优先。严格部署可以打开 `deps.requireAllowlist`，只允许名单内的包。
3. 审批提示显示：包名、解析出的版本、下载来源（索引地址）、文件哈希、依赖闭包的完整列表（含传递依赖）。
4. 批准后，`DependencyBroker` 解析并下载到宿主缓存，**只接受预编译包**（wheel）：包的安装只是解压文件，不运行包自带的任何构建脚本。源码包（sdist）的构建会执行包里的任意代码（背景知识，落地前验证所用工具的具体开关），默认禁止（`deps.allowSourceBuild=false`）。
5. 记录各文件的哈希，构建出只读的依赖层，目录名由锁定内容的哈希决定，之后同样的依赖直接复用，不再下载。
6. 沙箱启动时，SDK 按本次授权清单把依赖层加入搜索路径。依赖层里的 `.pth` 文件不处理（避免导入前自动执行代码，**【待验证】**对常见包的兼容性）。依赖层只读挂载。
7. 安装器本身在宿主运行，所以它是可信代码执行面：用清空的环境变量、不接触工作区、只访问配置的索引地址。有后端支持时放进同一个沙箱后端里运行。

局限与风险（详见 R14、R17）：

- 没有预编译包的库（很多需要本地编译的科学计算库在某些平台和架构上没有）会失败，错误要明确“没有适用于当前平台的预编译包”。
- 名称相似的恶意包（typosquatting）和被投毒的版本：靠名单、锁定哈希、审批时展示完整闭包缓解，不能杜绝。
- 依赖层对所有后续调用可见，同一对话里别的调用也会用到；这是缓存的代价。内容由哈希锁定，不会随调用改变。

#### 通用说明

- `python.interpreter = system` 或自定义路径时：不隔离用户站点包、不保证 ACL 与路径可读、预置档不可用（`needs.packages` 启用后同样不可用）；显示警告。
- 原生扩展模块可以加载（进程级沙箱不改变这一点）；但沙箱会让依赖网络或写 `HOME` 的库失败，错误信息要指向对应的 `needs` 项（1.4.4）。

## 10. 配置项定义

### 10.1 配置来源与优先级

CLI 参数 > 环境变量 > 项目级配置 > 用户级配置 > 内置默认值。文件格式沿用 `mcp.json` 的 JSON 与 camelCase 风格。

### 10.2 信任分层

- **用户级**（`~/.agent/sandbox.json`，仓库之外）：可信，可以放宽。
- **项目级**（`<workspace>/.agent/sandbox.json`）：**只能收紧，不能放宽**。理由：克隆来的第三方仓库可能自带配置，如果它能放开网络、挂载 `~/.ssh` 或打开 `allowDirectWrite`，沙箱就被配置文件绕过了。`sandbox-runtime` 对 `allowAppleEvents` 也有同样的提示（只应来自用户级配置，**【已核实】**）。
- 收紧的判定：能力集合取交集，数值型上限取较小值，布尔型“更严格的一方”获胜。

### 10.4 命令行与环境变量（命名待定）

- `--isolation <off|read|write|net>`：设置能力上限（8.1）；环境变量 `AGENT_ISOLATION`。
- `--share <name>=<path>[:ro|:rw|:stage]`，可重复：运维预挂的长期共享目录（7.3），不是兜底的常用路径。
- `--sandbox-config <path>`。
- 注意：现有 `--no-sandbox` 仅关闭路径守卫，保持不变（3.3）。`--no-approval` 会让 `run_python` 的升级项也不再询问，横幅需要明示。

### 10.5 示例

默认形态（缺口兜底，桥接关闭，不预挂任何目录）：

```json
{
  "sandbox": { "level": "write", "fallback": "deny" },
  "python": { "interpreter": "managed", "envProfile": "data" },
  "approval": { "baseline": "auto" },
  "limits": { "wallTimeSecs": 120, "memoryMb": 1024 }
}
```

放开联网（用户级配置；`deps.*` 是后置的按需安装才有的配置，示例在 9.6 启用后再用）：

```json
{
  "sandbox": { "level": "net" },
  "network": { "mode": "brokered", "deniedDomains": ["*.internal.example.com"] }
}
```

运维预挂一个大数据目录并开启桥接（进阶，用户级配置）：

```json
{
  "shared": [{ "name": "data", "hostPath": "./data", "mode": "ro" }],
  "bridge": {
    "enabled": true,
    "tools": { "allow": ["calculator", "list_files", "read_file", "grep"] },
    "approval": { "mode": "manifest" }
  }
}
```

一次 `run_python` 调用的参数形态（只展示接口，不含实现）：

```json
{
  "reason": "现有工具无法解析 xlsx 并按月汇总",
  "code": "<python source>",
  "needs": {
    "read": ["data/sales-2026.xlsx"],
    "exports": [{ "from": "summary.csv", "to": "reports/summary.csv" }]
  }
}
```

这次调用含升级项（读文件、导出），所以审批时会逐项展示；若 `needs` 为空，只用预置依赖，则自动执行。

## 11. 典型使用场景

先看三个按“缺口兜底”流程走完的例子，再看场景总表。

### 11.1 例一：纯计算，无需任何申请（基线自动执行）

任务：“算一下这批日期之间相隔多少个工作日，并排除这份节假日列表。”现有工具里只有 `calculator`，做不了。

1. 模型判断 `calculator` 不适用，调用 `run_python(reason="需要日期与工作日计算", code=..., needs 为空)`。
2. 无升级项，且隔离已确认生效，所以自动执行，没有任何询问。
3. 代码在标准库里完成，`set_result` 交回一个小结果。模型继续任务。
4. 若代码有笔误：结果里是只含用户代码帧的 traceback，模型改代码重试；连续失败到 5 次，结果末尾追加“请换思路”。

### 11.2 例二：处理用户文件，需要读文件、导出（升级调用）

任务：“把 `data/sales-2026.xlsx` 按月汇总，结果存成 CSV 放到 `reports/`。”预置的 `data` 档里有 openpyxl 与 pandas（9.6 的候选清单），所以不需要装包。

1. 第一次尝试直接读文件，沙箱里看不到：错误是“被沙箱拒绝：此访问需要在 `needs.read` 申请”。
2. 模型改成带 `needs`（`read`、`exports`，见 10.5 的调用示例）重新调用。
3. 审批提示显示：代码全文、`reason`、要读的文件及大小、导出目标 `reports/summary.csv`（若已存在，标明将覆盖）。人批准。
4. 宿主复制文件进 `inbox`，启动沙箱；代码把 `summary.csv` 写到 `outbox`。
5. 宿主校验产物，按 `needs.exports` 复制到 `reports/summary.csv`（路径已过守卫），把摘要和预览回给模型。
6. 如果代码出错后重试，`read` 与 `exports` 每次调用都重新询问（1.4.3）。这是首版有意的取舍：宁可多问几次，也不让一次批准覆盖范围不同的后续调用。

**如果预置档里没有需要的库**：例如任务需要一个小众的格式解析库。首版的处理是：结果里明确“包 X 不在预置依赖中，附预置包名单位置”，模型改用预置库实现，做不到就告知用户。这类失败会被审计记录（13 章），是后续决定要不要做按需安装的依据（9.6）。

### 11.3 例三：抓取一个页面（需要联网）

任务：“读取这个公开页面里的价格表。”

1. 代码用 `requests` 联网，沙箱里没有网络：错误提示“需要 `needs.network` 申请域名；沙箱内请用 `sandbox.http`”。
2. 模型改用 `sandbox.http`，在 `needs.network` 声明具体域名。若部署上限是 `write`，直接返回“本部署未开放联网，请告知用户”，不弹审批。
3. 上限够时，审批显示域名清单，批准后宿主代为执行请求并返回响应；拒绝内网和元数据地址；批准只在这次调用内有效。
4. 注意：页面内容是不可信文本，结果回给模型时带来源标注（R6）。

### 11.4 场景总表

| # | 场景 | 配置要点 | 流程与说明 |
|---|---|---|---|
| 1 | 纯计算、文本处理、日期/正则/统计 | 默认配置；`needs` 为空 | 基线自动执行（11.1）。绝大多数缺口任务属于这一类，也是兜底工具最常用的路径 |
| 2 | 格式转换、表格清洗、画图 | `envProfile=data`；`needs.read`；`needs.exports` | 文件复制进 `inbox`，产物经校验后按导出规则放回工作区（11.2） |
| 3 | 需要预置档之外的库（**后置，P5**） | `needs.packages`；`deps.*` 控制来源与名单 | 首版不提供：缺依赖时改用预置库或告知用户。有审计数据证明值得时，再按 9.6 的流程做：宿主侧准备依赖层，只接受预编译包，审批时展示闭包。优先把高频缺失的库加进预置档 |
| 4 | 抓取公开页面或调用接口 | 上限为 `net`；`network.mode=brokered`；`needs.network` | 请求由宿主代为执行；仅限获批域名；内网与元数据地址始终拒绝（11.3） |
| 5 | 对项目文件批量改动 | `needs.read` 读源码；`needs.exports` 回写 | 沙箱不直接写工作区；回写逐项展示、需批准；读拒绝清单与写回拒绝清单始终生效（7.5） |
| 6 | 一个对话里多轮迭代分析 | 默认 `workScope=conversation` | 同一对话共用 `work` 目录，上一轮的脚本和缓存的中间文件还在；每次仍是新进程 |
| 7 | 批处理且要省 token（进阶） | `bridge.enabled=true`；`needs.bridge` 声明只读工具 | 代码在沙箱内循环调用宿主工具，中间结果留在变量里，只把汇总返回模型。这是代码即 API 的核心收益，但不是兜底的主路径 |
| 8 | 运行 skill 自带的脚本 | `skills.roots`；`run_python(script=...)` | 脚本只读挂载，与 Agent 生成的代码同等不可信；需要的库必须在预置档里（后置的按需安装启用后可申请）|
| 9 | 无人值守（定时任务、批处理，根本没有前端） | `escalation.unattended=refuse` | 没有任何通道能提问，所有升级项直接拒绝；只能做基线任务，不会挂起。注意与“前端在、暂时没人答”区分：后者外层调用可以挂起恢复（`escalation.unanswered`，8.1） |
| 10 | 服务端多用户（对应 gap-analysis 第 11 项） | `backend=container`（或 microVM） | 进程级沙箱不足以隔离不同租户，改用更强后端；每租户独立数据目录 |

## 12. 安全风险与隔离边界

### 12.1 保证什么，不保证什么

**由 OS 强制的边界**（沙箱代码无法放宽）：授权之外的文件读写、网络访问、可见的进程和 IPC 对象、资源上限（受平台限制，见 8.3）。

**由宿主逻辑保证的**：`needs` 的校验与审批（含谓词与工具共用的解析、工具侧默认只授予基线）、读拒绝与写回拒绝清单、入站复制与出站回收校验、桥接白名单与策略链、依赖准备、配置的收紧规则、协议校验。这些依赖宿主代码正确，不是 OS 保证。

**基线自动执行的含义**：在默认配置下，Agent 现场写的任意代码**不经人看**就会在沙箱里运行。这条路径的安全性完全来自 OS 边界，所以 OS 边界的质量（第 8、9 章）和隔离是否确实生效（R8），比任何审批流程都更关键。如果团队不接受这个前提，可以把 `approval.baseline` 设为 `ask`，代价是每个缺口任务都要打断一次人。

**不保证的**：内核漏洞、侧信道、管理员权限攻击者、通过合法授权的通道外泄数据（见风险 R3）。

### 12.2 风险清单

| # | 风险 | 说明 | 缓解 | 残余 |
|---|---|---|---|---|
| R1 | 符号链接与竞争（TOCTOU）：共享目录、`inbox` 入站复制、`outbox` 与 P0 结果文件的读取、`exports` 落地写入 | 沙箱可以在可写目录里放链接，等宿主校验之后再替换；P0 的结果文件可以被建成指向宿主敏感文件的链接，宿主跟随读取就成了被借权的代理人；工作区里的其他进程可以在导出校验后替换目标路径 | 逐级 `O_NOFOLLOW`/`RESOLVE_BENEATH`；回收时复制而非原地使用；7.4 的出站与入站规则在 P0 就生效；导出落地从工作区根逐级不跟随链接地创建（7.2）；`stage` 默认；`rw` 默认禁用 | `rw` 模式下仍有风险，已要求显式确认 |
| R2 | 桥接提权（confused deputy） | 沙箱借宿主的权限做自己做不到的事 | 桥接默认关闭；硬拒绝 `run_command` 与 `run_python`；走同一策略链；声明即预批只限只读类（4.3 第 6 条）；限速与预算 | 被放行的工具本身的漏洞 |
| R3 | 经允许的通道外泄 | DNS、代理白名单域名、桥接的 `web_search`、stdout 内容、产物文件 | 网络默认关；出站工具默认拒绝；代理做解析地址检查；产物不自动进上下文；审计 | 白名单域名本身可作为外泄通道，无法完全消除 |
| R4 | 资源耗尽 | fork 炸弹、内存炸弹、磁盘写满、CPU 空转 | 8.3 的矩阵；整树回收；看门狗 | macOS 上内存与进程数约束较弱；没有可移植的磁盘配额 |
| R5 | 通道协议攻击 | 超大帧、深层嵌套、洪泛、乱序、慢读拖死宿主 | 5.8 的硬化；有界队列；违规即断 | 解析器自身漏洞，需模糊测试 |
| R6 | 经输出的间接提示注入 | 工具结果、stdout、产物内容里带攻击者文本，影响后续模型行为 | 来源标注；不自动读入上下文；`AfterToolCallback` 脱敏 | 模型仍可能被误导，由审批兜底 |
| R7 | 凭据泄露 | 环境变量、`.env`、`~/.ssh` | `env_clear` 加白名单；白名单读取；`needs.read` 的读拒绝清单（7.5；现有守卫读取时只拦 `.env*`，不够用）；桥接读工具与直接调用一致，仍受路径守卫 | 用户把凭据放进共享目录；直接调用的 `read_file` 仍可读 `mcp.json` 等（现状，不在本方案范围内） |
| R8 | 静默降级 | 内核太旧、用户命名空间被禁、AppContainer 授权失败，导致实际没有隔离。在“基线自动执行”的设计下尤其要紧：自动放行的前提就是隔离确实生效 | `probe()` 实测；`fail-closed`；横幅与状态命令显示实际隔离类型；启动自检（试图越权并确认被拒）；自检未通过、后端降级或 `level=off` 时，`approval.baseline` 强制回到逐次询问。审批谓词是同步的，隔离状态经共享原子状态传给它，运行中失效会翻转（1.4.3）；自检结果按（后端、profile 形状）缓存 | 自检只能证明自检当时的状态，之后被撤销的授权靠运行中的复测发现，两次复测之间有窗口 |
| R9 | 内核共享攻击面 | 进程级沙箱弱于虚拟机 | seccomp 收窄系统调用；及时更新系统；多租户用容器或 microVM 后端 | 内核 0day 不在范围内 |
| R10 | 持久化投毒 | 沙箱写入后被宿主工具后续执行（`.git/hooks`、`sitecustomize.py`、CI 配置） | 写回拒绝清单（7.5，`exports` 与共享挂载共用）；`stage` 加审批；skill 与运行时只读；数据目录默认放在工作区内时，基线自动执行写下的脚本可被后续经批准的 `run_command` 运行（审批人只看到命令行），所以数据目录倾向放到用户数据目录（7.1、15.2 第 13 项） | 清单可能不完整；数据目录放在工作区内时上述路径仍存在 |
| R11 | 进程逃逸出回收范围 | `setsid`、双 fork 脱离进程组 | Linux 用 PID 命名空间或 cgroup；Windows 用 Job；macOS 加父子扫描 | macOS 与 Landlock-only 兜底下有残余 |
| R12 | Windows 授权残留 | 为共享目录改动的 ACL 在崩溃后遗留 | 记录、撤销、启动时清理 | 崩溃与断电之间的窗口 |
| R13 | macOS profile 私有接口 | `sandbox-exec` 弃用，profile 语法随系统变化 | 集中生成、版本自检、失败即拒绝 | Apple 移除该接口时需要迁移 |
| R14 | 供应链（预置部分） | 受管运行时与预置依赖被投毒 | 哈希锁定；离线构建；只读挂载 | 构建时的上游风险 |
| R15 | 桥接带来的成本放大 | 代码循环调用模型类工具 | 默认拒绝 `AgentTool` 与视觉工具；限速与总次数预算；用量计入父运行 | 白名单内工具的成本由预算兜底 |
| R16 | 绕过沙箱：用 `run_command` 直接跑 Python | 模型手里还有不隔离的 `run_command`，可以 `python script.py`，沙箱边界被它“选另一条路”绕开；也包括 `node`、`bash` 等其他解释器 | 工具说明引导模型优先用 `run_python`；审批提示里对解释器命令加醒目警告；审计里统计两者的使用比例。后续选项：(b) 给 `run_command` 另做一个宽松的分级隔离档（可写工作区、可联网），(c) 启用沙箱时移除它（会损失 `cargo`、`git` 等开发类用法，不推荐） | 检测命令里的解释器名只是弱防护，不能当边界。**首版接受为已知残余风险**：只要 `run_command` 不隔离，这个风险就存在，审批是唯一的闸门 |
| R17 | 按需安装的供应链风险（**仅在后置的按需安装启用后适用**；首版没有这一项，风险面只剩 R14） | 名称相似的恶意包（typosquatting）、被投毒的新版本、依赖闭包里夹带的包；源码包构建时执行任意代码；安装器本身运行在宿主侧 | 只接受预编译包（`deps.allowSourceBuild=false`）；`deps.allow/deny` 与 `requireAllowlist`；审批展示完整依赖闭包、版本、来源、哈希；依赖层只读、按哈希复用；不处理依赖层里的 `.pth`；安装器清空环境、不碰工作区、只访问配置的索引 | 恶意包的代码仍会在沙箱里运行（所以只能拿到基线权限，加上本次被批准的升级项）；批准一个恶意包 + 联网同时出现时，外泄路径存在（见 R18） |
| R18 | 升级项组合造成外泄 | 单看每一项都合理：读文件 + 联网（或 + 装包后联网），合起来就是把用户文件发到外面；沙箱里的恶意依赖或被注入的提示正好利用这一点 | 审批提示把组合风险写明（“将读取 X 并向 Y 发送数据”）；`needs.network` 域名越具体越好，过宽通配符拒绝；读文件与联网同时出现时提高提示的醒目程度；`brokered` 模式下请求体大小与次数有上限并写审计 | 白名单域名本身可作为外泄通道；批准人看不出恶意意图时无法兜底 |
| R19 | 通过 `reason` 与 `needs` 影响审批 | 模型被提示注入后，在 `reason` 里写服从性的话术，或把危险申请夹在一堆正常申请里，利用人的审批疲劳 | `reason` 只展示不参与判定，用等宽、转义后的纯文本；申请项分行逐项展示，不用模型的自述替代；连续被拒的重复申请在结果里提示“已被拒绝，请勿重复”；`approval.baseline` 保持自动执行，减少无谓的审批次数，让人更认真对待真正的升级项；审批内容按工具渲染（代码按行、`needs` 逐项，1.4.3），不是直接打印原始 JSON | 人为因素无法完全消除 |
| R20 | 审批未接线或被绕开，升级项直接生效 | 审批是工具之外的回调。库使用者只注册了 `run_python`、没配审批规则；谓词与工具对同一份 `needs` 理解不一致（谓词放行、工具授权）；`needs` 内部形状错误或带未知键，没被整体参数的 fail-closed 覆盖 | 工具持有的授权上限默认只有基线，审批接线或明确免审批后才抬高（1.4.3 末条）；谓词与 `NeedsResolver` 共用解析函数，未知键与形状不符判为升级项；谓词没判为升级项的调用只授予基线；`--no-approval` 是唯一的“免审批”入口，横幅明示 | 调用方明确选择免审批后，安全性只剩 OS 边界与拒绝清单 |

### 12.3 明确的信任假设

宿主进程、本机内核、受管运行时的构建来源、用户级配置文件都被视为可信。其中任何一项被攻陷，本方案不再提供保证。

## 13. 可观测性与审计

- **span**：`execute_tool` 之下挂 `sandbox.exec`，再下面是 `sandbox.bridge_call`，沿用 `src/agent/runtime/observe.rs` 的体系。属性包含后端类型、等级、墙钟、CPU、峰值内存、退出原因、桥接调用数、被拒绝的访问数。
- **审计日志**（JSON Lines）：每次启动（含生效的 `Profile` 摘要）、每次桥接调用（名称、参数摘要、决定、耗时）、每次产物回收（路径、大小、sha256、是否被拒）、每次违规（协议违规、被杀原因）。`audit.redact` 默认开启。
- **违规提示**：沙箱内的访问被拒时，错误信息要告诉模型“被沙箱拒绝：此访问需要在 `needs` 申请 X；若本部署不允许，请转告用户”，但不展示宿主的无关路径（1.4.4）。
- **兜底效果指标**：每次调用记录 `reason`、是否含升级项、是否被批准或拒绝、失败类别、重试次数、墙钟与用量，用来回答“兜底工具到底在解决什么、哪里最常失败、哪类 `needs` 最常被拒”。`run_python` 与 `run_command` 的使用比例也记入（R16）。
- **状态命令**：显示实际生效的后端、是否降级、探测到的能力缺口。

| 3 | 审批谓词读取共享原子状态的集成测试：自检未确认或运行中翻转时，基线调用确实回到询问；`ApprovalRule::When` 加 `without_standing_approval` 的组合 | 影响基线自动执行是否能安全落地（15.2 第 1 项的前提） | 1.4.3、R8 |
| 4 | `data` 档在默认资源限制下的导入：`RLIMIT_AS`、线程数上限、`env_clear` 白名单、`HOME` 指向 `tmp` | 默认资源值要重定；`data` 档的内存限制方案要换 | 8.3、8.4、P0b |
| 5 | Linux 用户命名空间在目标环境（含 CI 镜像）是否可用；不可用时 Landlock 加 seccomp 兜底的实际能力 | 影响 CI 矩阵与降级路径的描述 | 9.3、9.5、14 |
| 6 | 审批内容渲染：终端与 Web 两端展示多行代码与逐项 `needs` | 影响 R19 的缓解是否成立 | 1.4.3、P1 |
| 7 | Windows：AppContainer 下 Python 运行与继承的命名管道（9.4 的待验证项），与 P0 并行启动 | 影响 P3 的范围 | 9.4、P3 |

### 15.2 待确认问题

下面按对设计影响的大小排序，每项给出倾向。

1. **基线自动执行**：**已定，接受。** `needs` 为空的调用不经人看就执行，安全性完全靠 OS 边界（12.1）。条件不变：仅在启动自检确认隔离生效时自动执行；自检未通过、后端降级或 `level=off` 时回到逐次询问。
2. **默认的联网上限**：**已定，保持 `write`，默认不能联网。** “抓取页面”这类任务在默认配置下会被拒并提示用户；交互式 CLI 用户通过 `--isolation net` 显式打开，每次联网仍逐次询问。
3. **`run_command` 与沙箱的关系（R16）**：`run_command` 要用宿主的工具链（`cargo`、`git` 等），无法直接套用默认沙箱，否则这些用法都会失效。三个选项：(a) 保持现状，靠审批把关，审批提示里对 `python`、`node` 等解释器命令加醒目警告，工具说明引导优先 `run_python`；(b) 另做一个宽松的分级档（可写工作区、可联网）给 `run_command` 用，这是此前计划的方向，但属于另一个项目；(c) 启用沙箱时移除 `run_command`，会损失开发类任务。倾向：先 (a)，(b) 放到 P5，并明确“只要 `run_command` 不隔离，`run_python` 的边界可以被绕开”是已知残余风险。
4. **取得对话标识与嵌套上下文**：P1 就需要 `conversation_id`（工作目录按对话保留），P4 才需要嵌套调用的上下文。选 task-local，还是扩展 `Tool` trait（破坏性变更，但一次解决两个需求）。倾向：先 task-local，需求累积后再评估扩展 trait。
5. **`needs.packages` 的批准记忆范围**（后置，随 P5 再定）：按锁定哈希在进程内记住（实现简单，谓词即可），还是按对话记住（要写成自定义的 `BeforeToolCallback`）。倾向：先进程内。首版没有 `packages`，此项暂不影响实现。
6. **Windows 第一版范围**：是否接受“仅 AppContainer，联网只走 `brokered`，没有 `proxy`”，还是要求把专用用户加 WFP 也做进来。倾向：接受前者。
7. **运行时分发与预置档内容**：受管 Python 随发行包带，还是首次使用时下载（需要联网与校验）。预置档做厚之后，这是首版体积的主要来源：以 9.6 的候选清单为起点，逐个确认三平台各架构的预编译包、体积、导入耗时和许可证；是否分成 `base`、`data`、`docs` 几档；pandas、scipy、scikit-learn 这类大库是否都带。需要先实测再定，我没有这些数据。
8. **`brokered` 网络的库兼容**：是否对 `requests`、`urllib` 等做垫片，让现成代码少改；还是只提供 `sandbox.http` 并靠错误提示引导（8.2）。倾向：首版不做垫片。
9. **许可证策略**：是否一律排除 GPL 依赖（决定 `birdcage` 是否完全出局，本文已建议不用）。
10. **CLI 开关命名**：`--isolation` 是否可以，以及与 `--no-sandbox` 的并存关系。
11. **按需安装的启动判据**：9.6 给的是定性条件（缺依赖失败占比高、缺失库分散）。要不要在审计里预先设一个具体阈值和观察期（例如连续多少次失败、观察多久）。阈值没有社区数据可参照，需要上线后自己定。
12. **helper 的落地方式（D3）**：本 crate 同时是库和 CLI，“宿主启动本程序的 helper 入口”对库使用者不成立。选项：(a) 随发行包分发独立的 helper 二进制，库按路径或环境变量找到它；(b) `arg0` 分发，使用者要在 `main` 首行调用一个入口函数，侵入性强；(c) 不用 helper，改在 `pre_exec` 里只做不需分配内存的系统调用（要先过 P0 的 PoC 1）。倾向：先做 PoC，若 (c) 可行则用 (c)，否则 (a)。
13. **数据目录放哪里（7.1）**：默认放工作区的 `.agent/sandbox/`，还是用户数据目录。放工作区内：`.gitignore` 要补规则，且沙箱写下的脚本可被后续经批准的 `run_command` 运行，审批人看不到脚本内容（R10）。放用户数据目录：工作区里不留可执行内容，代价是磁盘占用要跨工作区管理。倾向：用户数据目录。
14. **审批未接线时的默认行为（1.4.3 末条）**：库使用者只注册工具、没配审批规则时，升级项直接不可用（只做基线）。是否接受；另一种做法是此时连基线也要求显式声明，防止使用者不知道工具在自动执行代码。倾向：升级项不可用，基线可用，但构造函数的文档与示例里要写明。
15. **读拒绝清单是否同样应用到直接调用的 `read_file`（7.5）**：现状是 `.git/`、`.agent/`、`mcp.json` 可读（`mcp.json` 里有令牌），本方案只对 `needs.read` 收紧，不改守卫本身。直接调用的这个缺口是否另立项处理，不在本方案范围内，但要有人认领。
